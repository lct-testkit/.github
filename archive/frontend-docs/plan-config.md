# План агента B — «Настройка и данные»

Область: конструктор воронок, справочники, импорт каталогов, отчёты и дашборды, реестр ЕГРЮЛ (админ), интеграции (админ), шаблоны уведомлений.
Код: `src/lib/features/config/**`, маршруты `src/routes/(app)/{workflows,catalog,imports,reports}/**`, `admin/{registry,integrations,notification-templates}/**`.
Права (из `/api/me → scopes`): `workflow:read|write|publish`, `catalog:read|write`, `import:run|rollback`, `report:read|create`, `registry:import`, `integration:admin`, `notification_template:manage`, `file:download`.
Роли: KAM — читает воронки/справочники, строит отчёты; HEAD — + импорт; ADMIN — всё; AUDITOR — ничего из моей области (страницы скрыты в nav, на прямой переход — `ErrorState` 403).

## B. Карта экранов и потоков

Общие правила: списки — `Page` + `PageHeader` лида, фильтры в query string, `ResponsiveTable` (десктоп — таблица, телефон — карточки), skeleton при загрузке, `EmptyState` с действием, `ErrorState` с «Повторить», мутации — `toast`, опасные — `confirm()`; 409 `CRM-1002` — сообщение и «Обновить» без потери ввода; 403 — `ErrorState` без кнопок, если прав нет — кнопка не рисуется (`session.can`).

### B1. Список воронок `/workflows`
* Видит: карточки/строки: название, код, тип сделки (chip B2B/B2C), состояние (`StatusChip` черновик/опубликована/архив), «по умолчанию», дата публикации, число статусов (из `GET /workflows/{id}` не тянем — показываем без счётчиков, чтобы не было N+1).
* Главное: «Создать воронку» (ADMIN). Вторичные: открыть, фильтры (тип, состояние), поиск с дебаунсом.
* Состояния: загрузка — skeleton-строки; пусто — «Воронок нет» + «Создать»; ошибка — `ErrorState`.
* Телефон: карточки, FAB «+», фильтры в свёрнутой панели. Планшет/десктоп: таблица.
* Права: KAM/HEAD — только просмотр (открывают редактор в режиме чтения).

### B2. Редактор воронки `/workflows/[id]`
Раскладка десктоп: сверху компактная шапка (название, состояние, «Сохранить черновик» / «Опубликовать» / «Проверить» / меню «⋯»: «Автораскладка», «Экспорт JSON»), слева холст `SvelteFlow` (узлы-статусы, рёбра-переходы, `Background`, `Controls`, `MiniMap` только на десктопе), справа панель свойств 380 px (`Drawer`-подобная панель в потоке, не оверлей). Низкие окна: шапка одна строка, панель прокручивается внутри, кнопки действий закреплены внизу панели.
* **Узел-статус** (кастомный `nodeType: 'status'`): цвет-полоса слева (color статуса или токен по типу), название, код мелко, chip типа (initial/intermediate/won/lost/parked), бейдж SLA (часы), значок ошибки/предупреждения (issues), архивный — полупрозрачный с замком, не редактируется. Handles: source справа, target слева.
* **Ребро-переход** (кастомный `edgeType: 'transition'`): подпись = имя, пунктир если есть условия, значки: замок (роли), «!» (требует комментарий), молния (действия). Проблемное — красный.
* **Панель свойств узла**: Название (автогенерация кода транслитом для нового), Код (только латиница, уникален), Тип (SegmentedControl), Цвет (палитра из 8 токенов-цветов, не произвольный), Обязательные поля (Multiselect из каталога полей сделки + custom_fields.*), SLA (Accordion: срок в часах/днях с переключателем, порог %, эскалация на роль, каналы, «в рабочих днях», «активно»). Кнопки: «Архивировать статус…» (только у сохранённого; открывает мастер B3), «Удалить с холста» (только новый/без сделок — проверяем impact).
* **Панель свойств ребра**: Название, Из → В (только чтение, меняется перетаскиванием), Роли (Multiselect KAM/HEAD/ADMIN; пусто = все), «Требовать комментарий» (Switch), **Условия** — конструктор: группа «Все/Любое из» с вложением до 5 уровней, строка условия = [Поле (Select с группами: сделка, пользовательские поля, вложения)] [Оператор (зависит от типа поля)] [Значение (по типу: число, дата, текст, выбор `signed/…` для signature_status, список для in/not_in — `TagInput`)]; человекочитаемая сводка внизу («Сумма заполнена и (Договор подписан или есть вложение «Договор»)»). **Действия** — список карточек, «Добавить действие» (Select типа): *Создать задачу* (заголовок, исполнитель: роль или owner/manager/initiator, срок дней, приоритет), *Уведомить* (код события Select из известных, каналы, получатели), *Запросить подпись* (шаблон документа — Select из `/api/signature-templates` если лид/C дадут ручку в схеме, иначе текст; подписанты — список {роль | роль контакта | пользователь}, порядок, срок, при отклонении: «предыдущий статус» или статус воронки, при истечении), *Событие интеграции* (Select из 4 событий, payload — не редактируем). Никакого JSON, но есть «Показать JSON» (только чтение) для админов-энтузиастов.
* **Валидация на лету** (клиент, `workflows/validation.ts`): один initial, ≥ 1 терминальный, недостижимые, ловушки, дубли кодов/переходов, петли, корректность условий/действий, `on_rejected` на существующий статус; предупреждения для lost без причины и won без суммы/даты. Проблемные узлы/рёбра подсвечиваются, панель «Проблемы» (Accordion под шапкой или Drawer на телефоне) — клик по проблеме центрирует холст на узле. Серверный `validate` — по кнопке и перед публикацией; его строки маппим на узлы `parseServerIssues`.
* **Черновик/публикация**: любые правки → «есть несохранённые изменения» (бейдж, `beforeNavigate` с confirm). «Сохранить черновик» → `PUT /graph` с If-Match, версия обновляется. «Опубликовать» доступна, когда сохранено и локальных ошибок нет; предупреждения показываем в confirm. Опубликованная воронка редактируется дальше как черновик поверх (бэкенд: сделки живут по снимку) — в шапке подсказка «Изменения вступят в силу после публикации».
* **Автораскладка**: `layoutByLevels` — BFS от initial слева направо, терминальные в последнем столбце; позиции узлов храним в `localStorage` по id воронки (бэкенд позиций не хранит), при первом открытии — автораскладка.
* **Телефон/планшет (< 1024)**: холст только просмотр (пан/зум, без перетаскивания и соединения), под ним список «Статусы» (карточки, tap → панель свойств в `Drawer` снизу на всю высоту) и «Переходы» (сгруппированы по статусу-источнику). Создание перехода — из панели статуса: «Добавить переход → выбрать целевой статус». MiniMap скрыт.
* Состояния: загрузка — skeleton холста; ошибка — `ErrorState`; архивная воронка — баннер «Только чтение».

### B3. Мастер архивации статуса (Modal `fullHeight` на телефоне, 640 px на десктопе; `WizardStepsHorizontal` 4 шага)
1. **Влияние** — `GET impact`: «В статусе «Согласование КП» — 27 активных сделок, 3 с SLA под угрозой». Если `supported=false` — предупреждение. 0 сделок — сразу шаг 3 с текстом «Сделок нет, статус будет архивирован».
2. **Куда перенести** — Select целевого статуса из `suggested_targets` (не архивные, не сам); резервный статус (опционально) с подсказкой «для сделок, у которых не заполнены обязательные поля целевого статуса: <список required_fields>»; режим SLA (RadioButton: пересчитать / сохранить / сбросить) с пояснениями в одну строку.
3. **Предпросмотр** — сводка: N сделок → «Целевой», обязательные поля целевого статуса, SLA-режим, «переходы из/в статус станут историей», «действие необратимо, статус останется в истории сделок».
4. **Выполнение** — `POST archive` (If-Match версии воронки) → если `job_status=completed` — успех; иначе `Progress indeterminate` «Переносим сделки…» и опрос `GET /workflows/{id}` до `is_archived`; результат: «Перенесено N, ошибок M» (M — из первого ответа нет; после завершения показываем только факт). Затем перезагрузка графа (версия изменилась).

### B4. Справочники `/catalog/*` — единый паттерн
Один компонент-шаблон `DictionaryPage` (список + `Drawer` формы), конкретные страницы дают колонки и поля. Список: заголовок, поиск/фильтры (в URL), «Создать» (ADMIN), таблица (десктоп) / карточки (телефон), у активируемых сущностей — `Switch` в строке (PATCH с If-Match, оптимистично, откат при ошибке). Drawer (`fullHeight`, 480 px; на телефоне — во всю ширину): 3–6 полей в один столбец, автофокус на первом, Enter — сохранить, Esc — закрыть, кнопки «Сохранить»/«Отмена» закреплены внизу; ошибки полей — из `ApiError.fieldErrors()` под полями (`code` занят → под кодом). Без «портянок»: продукт — шаг 1 (код, название, направление, формат, цена) и раздел «Дополнительно» в Accordion (описание, длительность, валюта, срок действия, пользовательские поля).
* Продукты: колонки код · название · направление · формат · цена · активен. Фильтры: направление (Select по дереву), формат, активность, поиск.
* Направления: `Tree` (id/title/children), кнопка «+ подраздел» у узла (itemSuffix), правка по клику. Телефон: то же дерево (компонент адаптивен).
* Причины отказа: список, группировка по категории (заголовки), `sort_order` — стрелки «выше/ниже» (PATCH sort_order) вместо ввода числа.
* Производственный календарь: год (SegmentedControl текущий±1), месяцы с датами, «Добавить дату», праздники/переносы разными Badge. Мобильный — список.
* Пользовательские поля: вкладки по сущности; строка: код · подпись · тип · обязательное · активно; форма зависит от типа (select/multiselect → список вариантов; number → min/max; string → regex/max length; date → без доп.).
* Регионы: только таблица + поиск по названию (клиентский; список маленький).

### B5. Мастер импорта `/imports/new` (5 шагов `WizardStepsHorizontal`, на телефоне — компактный: номер/название текущего шага + счётчик)
1. **Файл**: тип сущности (Организации/Продукты — RadioButton-карточки), режим (upsert по умолчанию, пояснение одной строкой), `FileUpload` .xlsx/.xls/.csv ≤ 50 МБ; загрузка через `uploadFile` с `Progress`; после commit → `POST /imports` → шаг 2. Ошибки формата (CRM-1801) — под полем файла.
2. **Маппинг**: таблица «Колонка файла | Примеры (3 значения) | Поле системы (Select, с «— не импортировать —»)». Автоподбор с сервера + пресет (Select «Пресет», применяем клиентски). Подсветка: ключевое поле не сопоставлено (ошибка, «Далее» недоступна), одно поле выбрано дважды (ошибка), обязательное поле сущности не сопоставлено (предупреждение). Внизу: «Сохранить как пресет» (Checkbox + имя). «Далее» → `PUT mapping` → шаг 3. Телефон: список карточек «колонка → поле».
3. **Проверка**: авто-`dry-run` при входе (с `Loader`); итог тремя плитками: ok / с предупреждениями / с ошибками (+ всего); кнопка «Скачать отчёт об ошибках» если `result_file_id`; пояснение, что строки с ошибками будут пропущены; «Назад к маппингу» / «Применить» (недоступна при ok+warn = 0, CRM-1803).
4. **Применение**: `POST apply` → опрос `GET /imports/{id}` каждые 2 с; `Progress indeterminate` + счётчики; по `completed*` → шаг 5.
5. **Готово**: итог, ссылки «Открыть организации/продукты» (фильтр `source=import` — A), «Откатить импорт» (danger confirm), «Новый импорт».
Журнал `/imports`: таблица заданий, клик → карточка `/imports/[id]` (те же итоги, откат, скачивание отчёта). Права: HEAD/ADMIN.

### B6. Отчёты `/reports`
* Галерея шаблонов (карточки 3 колонки → 1 на телефоне): название, описание, форматы chips, «Запустить». Роль-ограниченные (`kam_summary`) сервер уже фильтрует.
* Drawer «Запуск отчёта»: параметры по `reports/params.ts` (deal_funnel: тип сделки + воронка (Select из `/workflows` published); monthly_dynamics: месяцев 1–36; stuck_deals: лимит), формат (SegmentedControl из `output_formats`), «Запустить». Ответ 201: `completed` → сразу «Готово: N строк» + «Скачать»; `queued` → прогресс (индикатор неопределённый, т.к. `progress_pct` не обновляется) с опросом; `failed` → текст ошибки, «Повторить».

* Лимит параллельных (CRM-1601 → 429): UI показывает «Слишком много отчётов в работе, подождите» и блокирует кнопку на 10 с (код в бэкенде пока не бросается — см. backend-issues #17).

## D. Риски и вопросы к контракту
* **Дашборды без данных** (issue #19) — главный риск демо: без `format: json`/`/data` графики в дашборде не построить честно. Фолбэк — PNG-картинки и плитки-счётчики.
* **Прогресс фоновых задач** (архивация статуса, импорт, реестр, отчёты) — везде опрос списка/карточки; нет ни SSE, ни задач с процентами (issues #1, #18, #22). Общий хук `usePolling(fn, interval, until)` сделаю в `features/config/shared/polling.svelte.ts`.
* **500 при удалении статуса со сделками** (issue #5) — обязательная клиентская проверка impact перед сохранением графа с удалёнными узлами.
* **Подсветка серверных ошибок валидации по тексту** (issue #2) — хрупко; основной путь — клиентское зеркало.
* **`signature_templates` для действия `request_signature`** — ручка `GET /api/signature-templates` (роутер `signature_templates_router`) — область C; мне нужен только список кодов/названий. Прочитаю схему из `schema.d.ts`, права — уточнить (если только ADMIN/HEAD — ок, редактор воронки и так ADMIN).
* **`custom_field_defs` с `workflow_id`** — привязка поля к воронке: показываем Select воронки в форме поля, в конструкторе в каталог полей условий берём поля сделки без привязки + привязанные к текущей воронке.
* **Демо-данные**: сиды дают 2 опубликованные воронки, 8 шаблонов отчётов, 3 неактивных источника, ~25 шаблонов уведомлений; справочники (продукты/направления/причины/праздники) сидов, судя по коду, не имеют — проверить на живом бэкенде; если пусто — на демо покажем создание.
