## b) Карта экранов и потоков

Общие правила для всех экранов: главное действие — одна primary-кнопка; списки — курсорная пагинация (`createPager`); фильтры — в URL; состояния загрузка/пусто/ошибка; на телефоне таблицы → `TableCards`, контролы `size="l"`; модалки/Drawer с `fullHeight` и закреплёнными кнопками внизу; права через `session.can(...)`, а сервер — истина.

### 1. `/sign/[token]` — внешний подписант (приоритет 1, демо-вау)

Кто: гость по ссылке (телефон в первую очередь). Свой минимальный layout `src/routes/sign/+layout.svelte` (ThemeProvider, без меню и без сессии).

Компоновка (одна колонка, `max-width: 720px`, на десктопе центр):
1. Шапка: «Документ на подпись», название, тип (`kp` → «Коммерческое предложение» и т.д.), срок до `deadline_at`, чип статуса.
2. Просмотр PDF: `PdfViewer` (canvas на страницу, ширина по контейнеру, ленивый рендер страниц при прокрутке, кнопки «−/+» масштаба, счётчик страниц). Ссылки на скачивание нет; `preview_url` не показывается. Считаю «время на странице» (`dwell`) только для отображения — сервер сам считает `dwell_seconds` по `viewed_at`.
3. Подписанты: шаги (`WizardStepsHorizontal` на десктопе / вертикальный список на телефоне) — имя, порядок, статус; мой — выделен.
4. Текст соглашения (`agreement_text`) — как есть, `Typography body-s`.
5. Действия (закреплены внизу на телефоне): **Подписать** (primary, `size="l"`), «Отклонить» (secondary).

Состояния по `my_status`:
- `sent`/`viewed` → активные кнопки;
- `signed` → «Вы уже подписали» + ссылка на проверку (id подписи не приходит — показываю только статус документа; см. риски);
- `rejected` → «Вы отклонили документ: {reject_reason}»;
- `locked` → «Подписание заблокировано после 3 неверных кодов. Инициатор уведомлён»;
- `expired`/`void` → «Срок подписания истёк» / «Документ аннулирован{: причина}»;
- документ `blocked_no_agreement` не бывает у активированного запроса.

Поток подписи: «Подписать» → `challenge` → панель OTP: «Код отправлен на {sent_to_masked} ({канал})», поле из 6 цифр (маска `000000`, автофокус, `one-time-code`), «Отправить повторно» с таймером 60 с (`Retry-After` при 429 или `expires_in_seconds`), счётчик «Попыток: 3» (клиентский, т.к. сервер не отдаёт остаток). Ввод 6 цифр → `sign` автоматически. Ошибки — человеческие тексты по коду (`features/signing/errors.ts`). Успех → экран «Документ подписан», ФИО (`signer_display`), время, кнопка «Проверить подпись» → `/verify/{signature.id}`.

Отклонение: Modal с обязательной причиной (TextArea, ≥ 3 символов) → экран «Документ отклонён».

Демо: если `debug_code` в ответе challenge → инлайн-уведомление «Демо-режим: код подтверждения {code}» с кнопкой «Подставить». В prod поле `null` — блока нет. Код в `console` не пишется.

Телефон 360/390: всё в одну колонку, PDF по ширине, кнопки во всю ширину, нижняя панель прилипает. Ландшафт 844×390: PDF ограничен по высоте (`60vh`) с внутренней прокруткой, панель действий не съедает экран. Десктоп: карточка 720 px по центру.

### 2. `/verify/[[id]]` — проверка подписи (приоритет 1)

Без id: поле «Идентификатор подписи» (UUID, валидация формата) + «Проверить» → `goto('/verify/{id}')`. Для вошедших дополнительно блок «Найти подпись по файлу» → `POST /api/signatures/verify` (multipart через `fetch`/`api` с `FormData`).

С id: `GET /public/verify/{id}` → большая карточка статуса:
- `valid` → зелёная «Подпись действительна»; `disputed` → оранжевая «Подпись оспорена (компрометация ключа)»; `void` → серая «Документ аннулирован»; `not_found` → «Подпись не найдена».
- Поля: подписант, дата/время (ru-RU, локальный пояс + UTC), метод («ПЭП, одноразовый код»), хэш документа (моноширинный, копировать).
- Блок «Сверить файл»: `FileUpload` (accept `application/pdf`) → `crypto.subtle.digest('SHA-256')` → «Хэш совпадает: это тот самый документ» / «Не совпадает: файл изменён или это копия со штампом (проверяйте исходный PDF)». Файл на сервер не уходит.
- Ссылка «Проверить другую подпись».

Адаптив: одна колонка везде; на десктопе 640 px по центру.

### 3. `DealSignatures.svelte` (`{ dealId }`) — блок «Подписание» в карточке сделки (приоритет 2)

Данные: `GET /api/deals/{id}` (только `signature_status`, `active_signature_document_id`) → если есть активный документ — `GET /signature-documents/{id}`. Истории документов по сделке нет (см. риски), показываю активный.

Вид: заголовок «Подписание» + чип статуса сделки (`signature_status`); карточка документа: название, тип, срок, хэш (сокращённо), подписанты как горизонтальные шаги со статусами (`signed` ✓, `sent/viewed` в работе, `rejected` ✗ + причина, `void`/`expired`); действия по статусу:
- `draft`/`blocked_no_agreement` → **Отправить**; для `blocked_no_agreement` — баннер + «Оформить соглашение» (ADMIN, ссылка на `/admin/edm?...`);
- `pending`/`partially_signed` → «Аннулировать» (`signature:void`); ссылка «Открыть» → `/signing/documents/[id]`; для запроса, где `signer_user_id == me` и статус открыт — «Подписать» → `/signing/requests/[id]`;
- `signed` → «Протокол», ссылка на проверку последней подписи (id подписи в `SignatureDocumentOut` нет — берём из протокола/после подписи; см. риски);
- `rejected`/`expired`/`void` → причина + **Отправить заново** (создаёт новый документ мастером).

Мастер «Отправить на подпись» (Modal `fullHeight`, 3 шага, `WizardStepsHorizontal`): 1) Источник: шаблон (Select из `/signature-templates`) или PDF (загрузка `uploadFile`, только `application/pdf`); название (по умолчанию из шаблона). 2) Подписанты: чипы-кандидаты «Руководитель (HEAD)», «Контакт сделки», «ЛПР организации», при наличии права — конкретный пользователь по id (ADMIN); порядок: SegmentedControl «По очереди / Одновременно»; предупреждение, если внешний подписант не первый при «по очереди» (ссылка ему не будет доступна — ограничение бэкенда). 3) Срок (InputNumberStepper дней, по умолчанию из шаблона) → «Создать и отправить» = `POST` + `send`; ответ с `sign_url` → модалка ссылки (один раз) с копированием и «Открыть в новой вкладке» (ссылку переписываю на маршрут SPA `/sign/{token}`, см. риски).

Права: `signature:create` — KAM/HEAD/ADMIN (AUDITOR блок не видит); `signature:void` — HEAD/ADMIN.

### 4. `/signing` — «Мне на подпись» и `/signing/requests/[id]` (приоритет 2)

Список: вкладки «Ожидают» (`sent`/`viewed`/`pending`) и «Все»; карточки: название документа (догрузка `GET /signature-documents/{document_id}` с кэшем), тип, срок, мой статус, кнопка «Открыть». Пусто: «Документов на подпись нет».

Страница запроса: тот же `SignPage`-компонент, что и публичная страница, но данные — `POST /signature-requests/{id}/view` и действия `challenge/sign/reject` по `/api/...`. Общий компонент `features/signing/SignFlow.svelte` с адаптером `SignApi` (`{ load, challenge, sign, reject }`) — публичный и внутренний адаптеры. `pending` (не моя очередь) → «Ожидает предыдущего подписанта».

### 5. `/signing/documents/[id]` — карточка документа

Реквизиты, подписанты (таблица: имя, идентификатор маскированный, порядок, статус, отправлено/просмотрено/решение, причина отказа), действия «Отправить»/«Аннулировать»/«Протокол». Хэш полностью с копированием. Ссылка «К сделке».

### 6. `/profile` — профиль, сессии, безопасность (приоритет 3)

Вкладки (`Tabs`, состояние в `?tab=`): «Профиль» (поля только чтение + тема оформления из `$lib/stores/theme`, когда появится), «Сессии» (карточки; текущая помечена; «Завершить» — иконка), «Безопасность» (форма пароля; после успеха — сводка последствий). Если `session.me.password_change_required` — баннер сверху и автопереход на вкладку «Безопасность» (нужен хук лида, см. c).

### 7. `/admin/users` и карточка (приоритет 4)

Список: фильтры в панели (телефон — кнопка «Фильтры» со счётчиком), таблица с сортировкой отключённой (бэкенд сортирует по дате создания), статус — `StatusChip`. Клик → карточка.

Карточка `/admin/users/[id]`: шапка (ФИО, роль, статус, email), вкладки «Данные» (форма PATCH с If-Match), «Действия» (кнопки по статусу: `invited` → «Отправить приглашение повторно»; `active` → «Заблокировать», «Сбросить пароль», «Передать дела и уволить»; `blocked` → «Разблокировать», «Передать дела и уволить», «Запрос на удаление»; `terminated` → «Запрос на удаление»; `anonymized` → ничего), «Безопасность» (последний вход, `must_change_password`, `perm_epoch`, согласие). Опасные действия — `confirm`/Modal с причиной. Себя блокировать нельзя (скрыто), последнего ADMIN — disabled + Tooltip.

Создание (Modal): минимум полей (ФИО, email, роль); команда/руководитель/должность — в «Дополнительно» (Accordion), для HEAD команда обязательна. Идемпотентность: `headers: idem()`.

**Мастер offboard `/admin/users/[id]/offboard`** (`WizardStepsHorizontal`, 4 шага, контент прокручивается, кнопки внизу):
1. «Что держит сотрудник» — `preview`: карточки-счётчики «Сделки N», «Задачи M», «Импорты», «Отчёты», «Запросы подписи K»; список критичных сделок (`details`: номер, название, статус); `warnings` бэкенда — жёлтым; `supported=false` → предупреждение «модуль сделок недоступен».
2. «Преемник» — Select с поиском (`/admin/users?q=&status=active`, роли KAM/HEAD), причина увольнения (обязательна, ≥ 3). Нельзя выбрать самого сотрудника.
3. «Предпросмотр» — «Будет переназначено N сделок на {преемник}», критичные выделены; «Запросы подписи по роли будут переадресованы, персональные — нет (инициатору придёт задача)»; «Учётная запись → уволен, сессии завершены».
4. «Подтверждение» — чекбокс «Я понимаю, что действие необратимо» → **Подтвердить** (`confirm`) → результат: переназначено сделок (список id ссылками на `/deals/{id}`), запросов подписи, сессий; статус. Ошибки: 422 «преемник неактивен», 409 `CRM-1903`.

### 8. `/admin/erasure` — удаление и обезличивание

Список с отсчётом («Исполнение через 12 дн.»; `blocked` — красные чипы блокеров; `completed` — «Акт»). Карточка: шаги процесса как `WizardStepsHorizontal` (Запрос → Блокеры → Отсрочка → Исполнение → Акт) с текущим шагом по статусу; блокеры с подсказками: `active_deals` → «Передайте дела» (ссылка на мастер offboard), `open_tasks` → «Закройте или переназначьте задачи», `last_admin` → «Назначьте другого администратора», `has_signatures` → «Подписи не обезличиваются (ст. 6 ч. 1 п. 5, 7 152-ФЗ) — режим недоступен», `account_active` → «Сначала заблокируйте или увольте». Действия: «Пересчитать», «Отклонить», «Восстановить», «Акт».

Создание: «Новый запрос» → шаг «Субъект» (сотрудник / контакт / ИП + поиск) → форма: режим (RadioButton «Обезличивание» — по умолчанию / «Жёсткое удаление» с пояснением «только без зависимых записей»), причина, правовое основание (подсказки-чипы: «ст. 21 152-ФЗ», «отзыв согласия (ст. 9)», «истечение срока хранения»), комментарий → отправка → 409 `CRM-1902` → экран «Ожидает второго администратора» с `approval_id`; после подтверждения инициатор из `/admin/approvals` нажимает «Выполнить» → форма снова (режим предзаполнен) → создан → карточка запроса с блокерами.

### 9. `/admin/approvals` — «четыре глаза»

Список карточек: заголовок операции (человеческий), инициатор (имя через `/admin/users/{id}` с кэшем), создано, истекает (обратный отсчёт), статус-чип (`pending`/`approved`/`rejected`/`expired`/`consumed`). Кнопки по правилу `approvalActions(a, meId)`: чужая pending → «Подтвердить»/«Отклонить»; своя pending → «Ожидает второго администратора»; своя approved → «Выполнить»; остальное — без действий. Поток создания ADMIN: форма → 409 → страница «Заявка создана, попросите второго администратора подтвердить» с ссылкой на `/admin/approvals`; второй админ (в демо — другой пользователь) подтверждает; первый жмёт «Выполнить» → форма с `approval_id`.

### 10. `/admin/audit` — журнал

Панель фильтров (сворачиваемая на телефоне), таблица; строка раскрывается в детали. Экспорт с `confirm`. Блок «Целостность цепочки» — кнопка + результат. HEAD: без экспорта (право). Акторы: ADMIN — имена через кэш `/admin/users/{id}`; AUDITOR — короткий id + роль (нет права `user:read`, см. риски).

### 11. `/admin/teams`, `/admin/settings`, `/admin/edm` — см. чек-лист. Настройки: две вкладки + спец-форма политики ПДн. EDM: список + модалка создания + отзыв; для AUDITOR — только чтение.

### 12. `/invite/[token]`

Карточка: «Здравствуйте, {full_name}», «Приглашение для {email_masked} действует до {expires_at}», кнопка «Перейти ко входу». Ошибка → «Ссылка недействительна или истекла. Попросите администратора отправить приглашение повторно».

## c) Что нужно от общего слоя / лида

1. **Публичные маршруты без сессии.** Корневой `+layout.svelte` не должен требовать вход и не должен дергать `/api/me` для `/sign/**`, `/verify/**`, `/invite/**` (и не редиректить на `/login` при 401 оттуда). Нужны глобальные `ThemeProvider` и `ToastNotificationsProvider` на этих маршрутах.
2. **`api` для не-JSON ответов**: экспорт NDJSON (`GET /admin/audit/export`) и multipart (`POST /api/signatures/verify`, `FormData`). Нужна возможность `parseAs: 'blob'`/`'text'` и передача `FormData` без `Content-Type: application/json`; плюс способ получить сырой `Response`/`Retry-After` (для таймеров 429).
3. **CSRF после смены пароля**: `POST /api/me/password` переиздаёт cookie сессии и `crm_csrf` → заголовок `X-CSRF-Token` должен читаться из cookie на каждый запрос, а не кэшироваться при входе.
4. **`ApiError`**: нужны `retryAfter` (секунды из заголовка) и `extra` (`approval_id`, `status`, `current_version`, `user_id`).
5. **Публичные вызовы без авторизации**: `api` не должен подставлять `Authorization`/CSRF на `/public/*` (или отдельный клиент `publicApi`). Также ошибка 401/403 на `/public/*` не должна включать глобальный редирект.
6. **`password_change_required` / `consent_required`**: после входа общий слой ведёт на модалку согласия; при `password_change_required` — прошу редирект на `/profile?tab=security` с баннером (страница моя).
7. **Vite proxy для S3** (dev): presigned-ссылки на PDF ведут на `http://localhost:8333/<bucket>/…` — другой origin без CORS. Прошу добавить в `vite.config.ts` proxy для путей-бакетов `/signatures`, `/files`, `/reports`, `/imports` → `http://localhost:8333` с `changeOrigin: true` (SigV4 подписывает `Host`, путь не режем). Я на клиенте переписываю origin presigned-ссылки на текущий (`toSameOrigin`). Для prod — то же правило в Caddy (см. backend-issues).
8. **`nav.ts`**: подтвердить пути: `/profile`, `/signing`, `/signing/requests/[id]`, `/signing/documents/[id]`, `/admin/users`, `/admin/users/[id]`, `/admin/users/[id]/offboard`, `/admin/teams`, `/admin/approvals`, `/admin/audit`, `/admin/erasure`, `/admin/erasure/[id]`, `/admin/settings`, `/admin/edm`. Бейдж «ожидают подтверждения» в меню — если предусмотрен слот, я дам функцию-счётчик.
9. **`session.me`**: нужны `id`, `role`, `scopes`, `password_change_required`, `team_id`; `session.can()` по строкам из `Permission` (`user:write`, `erasure:manage`, `audit:export`, `settings:write`, `signature:create|sign|void`, `edm:admin|read`).
10. **Режим demo** (`config.mode`): читать из общего слоя, чтобы показывать предупреждения (смена пароля демо-учётки, `debug_code`).
11. **Компоненты `src/lib/ui`**: `StatusChip` с произвольной картой цветов, `DateText` с относительным временем («через 12 дн.»), `CopyButton` (если нет — сделаю у себя), `EmptyState`/`ErrorState`.
12. **Чтение чужих ручек**: `GET /api/deals/{id}`, `/api/contacts?q=`, `/api/organizations?q=`, `/api/regions` — читаю напрямую, ничего не меняю.

## d) Риски и вопросы к контракту бэкенда

Подробно с файлами и строками — `docs/backend-issues.md`. Кратко, по убыванию влияния:

1. **PDF на публичной странице не загрузится**: `preview_url` — presigned-ссылка на `:8333` (другой origin), SeaweedFS без CORS, а CSP бэкенда `default-src 'self'` запрещает `connect-src` к нему; плюс `Content-Disposition: attachment`. Нужен same-origin путь к файлу (проксирование бакетов через Caddy/Vite или ручка `GET /public/sign/{token}/file`).
2. **`sign_url` и `verify_url` указывают на JSON-ручки API** (`{base_url}/public/sign/{token}`, `{base_url}/public/verify/{id}`), а не на страницы SPA `/sign/{token}` и `/verify/{id}` — QR в штампе/протоколе ведёт на JSON. На клиенте переписываю `sign_url`; QR исправить может только бэкенд.
3. **Нет списка документов по сущности** (`GET /signature-documents?entity_type&entity_id`) — в карточке сделки виден только активный документ; истории (аннулированные/просроченные) нет.
4. **Проверка по файлу ищет хэш исходного PDF**, а пользователь скорее всего загрузит копию со штампом (`signed-*.pdf`) → `hash_mismatch`. Нужно индексировать и хэш штампованного файла.
5. **OTP: не возвращается остаток попыток** (`attempts`/`max_attempts`) и `max_attempts` в `ChallengeResponse` — счётчик на клиенте приблизительный.
6. **Внешний подписант не первый в `sequential`** → его ссылка никому не отдаётся (только warning в логе), ручки «переиздать ссылку» нет. В мастере предупреждаю и предлагаю «параллельно».
7. **Аудит без имён акторов**; AUDITOR не имеет `user:read` — увидит только UUID.
8. **`GET /me/signature-requests`** — без названия документа и без пагинации (N+1 догрузок).
9. **Нет `PATCH /api/me`** (имя, часовой пояс, телефон): у внутренних подписантов нет телефона ⇒ OTP всегда «email», а email-канал — заглушка (в demo спасает `debug_code`).
10. **Четыре глаза до валидации**: `POST /admin/users` с ролью ADMIN создаёт заявку раньше проверки дубликата email/команды — заявку можно подтвердить, а выполнение упадёт.
11. **`ErasureRequestOut` при создании** отдаёт `grace_until` даже для `blocked` (в БД `None`); список запросов без имени субъекта и без фильтра по субъекту.
12. **Приглашение в закрытом контуре**: `/invite/{token}` только проверяет токен и ведёт на вход, но у пользователя без письма Keycloak нет пароля — вход невозможен.
13. **Demo-режим и пароль**: `POST /me/password` меняет пароль реальной демо-учётки (сломает вход в один клик для всех); `reset-password` ставит `UPDATE_PASSWORD` и ломает password grant демо-учётки. На демо эти действия показываю с предупреждением.
14. `auto_unblock_at` при блокировке нигде не исполняется (только аудит) — подпись поля «справочно».
