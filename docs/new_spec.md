**Критерии успеха (measurable):**
1. p95 времени ответа API на операции «переход по статусу» и «добавление комментария» ≤ 300 мс при 50 RPS; end-to-end в браузере ≤ 1 с. **Выполнено по API:** на замерах 16–18.10.2026 (реалистичный поток 50 RPS, 3 реплики `api`, 4 vCPU) p95 комментария — 29 мс, перехода — 100 мс; на сервере стенда с реальным диском — 40 и 220 мс; при искусственном «залпе» из 50 одновременных запросов p95 0,65–0,96 с (последовательная запись в цепочку аудита). Замеры сняты на коде от 29.09 с Postgres на tmpfs — подробности и оговорки в [README, «Нагрузочное тестирование»](../README.md#нагрузочное-тестирование). Отдельного замера «≤ 1 с в браузере» нет — не проверено.
2. 100% действий, изменяющих данные, попадают в неизменяемый аудит-лог. **Выполнено:** запись пишется в той же транзакции, права `UPDATE`/`DELETE`/`TRUNCATE` отозваны, триггеры на каждой партиции, цепочка хэшей (HMAC) проверяется `GET /api/admin/audit/verify-chain`; построчного теста «каждая ручка пишет аудит» не выполнялось — не проверено.
3. Конструктор workflow позволяет собрать текущую 14-шаговую воронку без правки кода. **Выполнено:** все три воронки (две B2B и B2C) создаются сидами и правятся в редакторе графа; публикация — со снимком и `graph_hash`.
4. Импорт каталога 5 000 строк .xlsx с маппингом полей и отчётом об ошибках — без падений на «битом» файле и на CP1251. **Реализовано:** лимиты 100 000 строк и 50 МБ, `.xls`/`.xlsx`/`.csv`, CP1251 и UTF-8 BOM, отчёт `.xlsx` по строкам с ошибками; замер именно на 5 000 строк в этом документе не подтверждён — не проверено.
5. Полная развёртка `docker compose up` на чистой машине без интернета (из локального registry / сохранённых образов). **Выполнено:** офлайн-бандл релиза (все образы, подпись cosign, `install.sh`) — репозиторий `deploy`, `RUNBOOK.md`; сборка образов (не рантайм) требует сети.

# ЧАСТЬ 1. ДОМЕННАЯ МОДЕЛЬ И ГЛОССАРИЙ

Прежде чем стек — язык. Половина ошибок в CRM рождается из того, что «заявка», «сделка» и «лид» в разных головах значат разное.

| Термин | Определение в системе | Синонимы, которые НЕ используем |
|---|---|---|
| **Организация (Organization)** | Юрлицо-контрагент: вуз, компания, ИП. Корневая B2B-сущность | «Клиент», «Вуз» (вуз — частный случай, `org_type`) |
| **Контакт (Contact)** | Физлицо, связанное с организацией или самостоятельное (B2C). Носитель ПДн | «Лид» |
| **Сделка (Deal)** | Единица воронки: «продвижение продукта X организации Y». Ровно одна сделка = один экземпляр workflow | «Заявка» (используем как UI-лейбл, в коде — deal) |
| **Продукт (Product)** | Образовательный продукт ИТ Школы (курс, программа, трек) | — |
| **Направление (Direction)** | Направление подготовки/ИТ-специализация, к которой относится продукт | — |
| **Workflow** | Именованный граф статусов и переходов. Привязан к типу сделки (B2B/B2C) | «Воронка», «Пайплайн» |
| **Статус (Status)** | Узел графа. Имеет тип: `initial`, `intermediate`, `won`, `lost`, `parked` | «Стадия», «Этап» |
| **Переход (Transition)** | Направленное ребро: из статуса A в B, с правами, условиями и действиями | — |
| **КАМ (Key Account Manager)** | Роль. Ответственный за сделку | «Менеджер» |
| **SLA-правило** | Ограничение времени пребывания сделки в статусе; нарушение → эскалация | «Таймер» |
| **Сопоставление (Mapping)** | Процедура переноса сделок со снятого/изменённого статуса на актуальный | «Миграция» (внутренне — да) |

**Воронка `b2b_university_v1` (14 шагов).** Это дополнительная продажная воронка B2B (seed, не хардкод; ПЭП-согласование КП на переходе `kp_preparation → kp_approval`), **не используется по умолчанию**. Основная воронка по умолчанию — `b2b_university_v2`: ровно 14 шагов задания кейса (`rtk_requiriments.md`, раздел 2; список и сроки шагов — `backend/app/modules/workflow/seed.py`), с SLA на каждом шаге. Шаги `b2b_university_v1`:

1. Идентификация вуза → 2. Первичный контакт → 3. Квалификация (есть ли потребность) → 4. Назначение встречи → 5. Проведение встречи/презентации → 6. Сбор требований → 7. Формирование коммерческого предложения → 8. Согласование КП → 9. Юридическое согласование договора → 10. Подписание договора → 11. Передача материалов/доступов в LMS → 12. Запуск обучения → 13. Мониторинг успеваемости (данные из LMS) → 14. Закрытие периода / отчётность и пролонгация.

Терминальные: `won` (14 пройден), `lost` (отказ с обязательной причиной), `parked` (заморожено до даты).

**Воронка B2C** (`b2c_individual_v1`, короткая, 6 шагов): Заявка с сайта → Верификация контакта → Консультация → Оплата/договор оферты → Зачисление в LMS → Завершение обучения.

# ЧАСТЬ 2. АРХИТЕКТУРА

## 2.1. Уровень 1 — Системный контекст

Кто с кем разговаривает:

- **Пользователь (браузер)** → HTTPS → Caddy → статика SPA (SvelteKit, `adapter-static`; SSR нет) и `/api/*` → FastAPI.
- **FastAPI** сам является BFF: OIDC с Keycloak (обмен кода на токены, сессия в Redis, браузер получает только httpOnly-cookie), отдельного Node-процесса нет.
- **FastAPI** → PostgreSQL, Redis, SeaweedFS (S3), Keycloak Admin API.
- **Worker (arq)** → те же хранилища + исходящие интеграции.
- **Внешние системы:**
  - Сайт на Laravel CMS — **входящий** поток лидов B2C (webhook) + **исходящий** опрос REST/JSON.
  - LMS — **входящий** поток прогресса обучения (pull по расписанию).
  - Bitrix24 — коннектор внутри `api`/`worker` (модуль `integration`, включается `BITRIX_CONNECTOR_ENABLED`, по умолчанию выключен): исходящая синхронизация создания/обновления сделки (outbox → `crm.item.add`/`crm.item.update`) и входящий вебхук в упрощённом собственном контракте. Двусторонней синхронизации «в реальном времени» нет, отдельного контейнера-адаптера нет.
  - SMTP-релей (на стенде — Mailpit; на боевой установке — корпоративный сервер, `SMTP_*`) и SMS-шлюз (заглушка `sms-gateway-mock`). Канал Telegram — заглушка, реальной отправки нет.
  - LLM-инференс: **не реализован** — в конфигурации есть заготовка (`LLM_ENABLED`, `LLM_BASE_URL`, `LLM_MODEL`), код её не использует.

Принципиальное решение: **ядро не знает ни о Bitrix, ни о LMS, ни о Laravel**. Оно знает только о своём `integration`-модуле, который оперирует абстракциями `InboundMessage` / `OutboundEvent`. Это Anti-Corruption Layer. Коннектор отключается флагом источника в `integration_sources` и переменной окружения — ядро продолжает работать (отдельного контейнера для выдёргивания из compose нет).

## 2.2. Уровень 2 — Контейнеры (docker compose)

Состав сверен с `backend/docker-compose.yml` (разработка и демо) и `deploy/compose/docker-compose.yml` (боевой профиль: образы по digest из `deploy/images.yaml`).

| Контейнер | Образ/технология | Назначение | Состояние |
|---|---|---|---|
| `caddy` | Caddy 2.11 | TLS (`tls internal` или ACME), единая точка входа, HSTS и заголовки безопасности, `X-Request-Id` (UUID), балансировка `least_conn` по репликам `api`; ограничение частоты запросов — на уровне приложения (Redis), не Caddy | stateless (volume сертификатов) |
| `web` | при сборке — Node 22 + SvelteKit (`adapter-static`); в образе — статика SPA на Caddy, порт 3000 | клиент (SPA), отдаёт `config.json` | stateless; профиль `web` в `backend/docker-compose.yml`, в боевом compose входит по умолчанию |
| `api` | Python 3.12 + FastAPI + Uvicorn, 1 процесс на контейнер (`UVICORN_WORKERS=1`), масштабируется репликами | основное API, бизнес-логика, BFF (OIDC, сессии) | stateless |
| `worker` | тот же образ, команда `arq` | фоновые задачи и cron: импорт, отчёты, уведомления, outbox, синхронизации, SLA-скан, очистка по сроку хранения (`backend/app/worker/main.py`); отдельного контейнера `scheduler` нет | stateless |
| `migrate`, `seed` | тот же образ | разовые: миграции Alembic и сиды (воронки, шаблоны отчётов и уведомлений) | — |
| `postgres` | PostgreSQL 16 | базы `crm` и `keycloak` в одном экземпляре (отдельного `kc-db` нет); порт на хосте — только `127.0.0.1:5433`; в HA — Patroni | **stateful** |
| `keycloak` | Keycloak 25.0, realm `crm`, импорт `realm-crm.json` | IdP, OIDC, учётные записи, русская тема писем `rtk-crm` | stateful (в базе `keycloak`) |
| `redis` | Redis 7 (`--appendonly yes`, `maxmemory 512mb`) | кэш, сессии, очередь arq, rate-limit, локи, идемпотентность | **stateful** |

Из проекта **не реализованы** как отдельные контейнеры: `scheduler`, `kc-db`, `bitrix-connector` (коннектор — модуль `integration` внутри `api` и `worker`, включается `BITRIX_CONNECTOR_ENABLED`), `loki`/`vector`, `victoria-metrics`. `clamav`: клиент сканера есть (`CLAMAV_ENABLED`, по умолчанию `false`), сервиса ClamAV в compose и `images.yaml` нет.

**Сети.** Одна сеть `crm` (`bridge`); разделения на `edge`, `app` и `data` нет. Наружу опубликованы только порты Caddy (8080 и 8443; S3 через Caddy на 8333) и PostgreSQL на `127.0.0.1`; в боевом compose Postgres также привязан к loopback.

**Почему не микросервисы.** ТЗ допускает монолит с feature-flags. При 50 пользователях микросервисы дают минус: распределённые транзакции, сетевая латентность против SLA в 1 секунду, тройные расходы на observability. Берём **модульный монолит**: внутри `api` 13 модулей — `identity/`, `crm/`, `workflow/`, `catalog/`, `reporting/`, `integration/`, `notification/`, `audit/`, `admin/`, `files/`, `imports/`, `registry/`, `signing/`, каждый со своими `models / service / router / tasks`. Кросс-модульные вызовы — только через публичные сервисные интерфейсы, запрещены импорты чужих репозиториев (линтер: `import-linter`, 16 контрактов в `backend/.importlinter`, в CI — job `architecture`). Это оставляет дверь для вынесения модуля в отдельный сервис без переписывания — и это ровно тот аргумент, который нужен на защите.

## 2.3. Уровень 3 — Обоснование стека (готовые формулировки для защиты)

ТЗ явно требует аргументации. Аргумент «мы знаем только этот язык» запрещён, поэтому каждая позиция — через требование ТЗ.

**FastAPI / Python 3.12** *(разрешён ТЗ напрямую)*
- ASGI-асинхронность: при 50 конкурентных пользователях и 10 параллельных отчётах основная нагрузка — I/O-bound (БД, S3, внешние API). Async-модель держит это меньшим числом воркеров, чем синхронный WSGI.
- Pydantic v2 — единый источник истины схем: из них автоматически рождается OpenAPI 3.0.3 (`backend/openapi.json`, 287 операций), из OpenAPI — типизированный TS-клиент для фронта (`openapi-typescript`, `openapi-fetch`). Контракт не расходится с кодом физически.
- Экосистема под конкретные требования ТЗ: `openpyxl`/`xlrd` — импорт .xlsx/.xls с маппингом (`pandas` не используется); `xhtml2pdf` (вместо `WeasyPrint`: тот требует системных библиотек Pango/Cairo) — .pdf-отчёты; `matplotlib` (без `plotly`) — графики в .png/.pdf; `SQLAlchemy 2.0 + Alembic` — версионируемые миграции.
- Требование «LLM в закрытом контуре»: не реализовано (см. §2.1); Python остаётся подходящей средой для локального инференса.

**SvelteKit** *(отклонение от рекомендованного React — главный пункт для аргументации)*
- Ключевой NFR — отклик ≤ 1 с. Svelte компилируется в императивный JS без Virtual DOM: бандл 2–5× меньше сопоставимого React-приложения, TTI ниже. Для CRM, которую открывают с корпоративных ноутбуков в вузах (часто слабое железо и VPN-канал), это прямое попадание в SLA.
- SSR «из коробки» + `load`-функции: первый экран карточки сделки отдаётся сервером уже с данными — нет каскада «пустой скелет → запрос → рендер».
- SvelteKit `hooks.server.ts` даёт **готовый BFF-слой в том же процессе**: токены Keycloak не покидают сервер, в браузере только `httpOnly; Secure; SameSite=Lax` cookie с идентификатором сессии. Реализовать это на React пришлось бы отдельным Node-сервисом — это лишний контейнер и лишняя точка отказа.
- Риск «React в ТЗ» закрываем: компонентная архитектура, TypeScript, покрытие тестами, документированный design-system-слой — то есть все инженерные практики, ради которых ТЗ и указывает React, соблюдены.

> **Реализовано иначе.** Клиент собран как SPA (`@sveltejs/adapter-static`, fallback `index.html`) и отдаётся статикой из образа `web` (Caddy); SSR и `hooks.server.ts` не используются, поэтому преимущество «первый экран приходит с данными с сервера» не получено. BFF (OIDC, серверная сессия, cookie `crm_sid`) находится в backend (`/api/auth/*`) — отдельного Node-сервиса и лишнего контейнера нет, как и планировалось.

**PostgreSQL 16** *(рекомендован ТЗ)* — JSONB для кастомных полей сделок без миграций схемы; `tsvector` + `pg_trgm` для полнотекстового поиска по вузам/сделкам без Elasticsearch; декларативное партиционирование для `audit_log`; шифрование чувствительных полей — в приложении (Fernet), не `pgcrypto`; row-level triggers для истории статусов. Одна БД закрывает три требования (поиск, гибкие поля, аудит) — минус три контейнера.

**Redis 7** — ТЗ требует «кэш работы действий пользователя». У нас он несёт пять функций: (1) кэш карточек и справочников, (2) хранилище серверных сессий BFF, (3) брокер очереди arq, (4) rate-limit и защита от брутфорса, (5) распределённые локи и idempotency-ключи. Один компонент — пять требований.

**SeaweedFS вместо MinIO** — S3-совместимый API (код от смены не зависит), но лицензия Apache 2.0 против AGPLv3 у MinIO: для решения, которое заказчик будет разворачивать у себя в закрытом контуре, AGPL — юридический риск. Плюс SeaweedFS радикально эффективнее на большом числе мелких файлов (сканы договоров, вложения) за счёт архитектуры needle-storage.

**Keycloak 25** — обязателен по ТЗ. Разворачивается в своём контуре; своя база `keycloak` в том же экземпляре PostgreSQL (отдельного `kc-db` нет); realm `crm` как код (импорт `deploy/keycloak/realm-crm.json` при старте — воспроизводимость окружения).

**Caddy** — автоматический TLS (в т.ч. internal CA для закрытого контура), конфиг в 20 строк против 200 у nginx, HTTP/3.

**Docker Compose** — ТЗ допускает вместо k3s/minikube; profiles (`web`, `integrations`, `site`, `mail`, `monitoring`, `ha`, `registry`, `demo-data`) заменяют feature-flags на уровне инфраструктуры.

# ЧАСТЬ 3. СКВОЗНЫЕ МЕХАНИЗМЫ

Эти механизмы определяют, будет ли система «взрослой». Они описываются один раз и применяются везде.

## 3.1. Аутентификация: полный поток

**Паттерн — BFF (Backend-for-Frontend), не SPA-с-токенами-в-localStorage.** Причина прямая: токен в localStorage крадётся любым XSS, а мы — ИСПДн.

Поток входа:
1. Клиент без сессии вызывает `GET /api/auth/login`: backend сохраняет `state`, `nonce` и PKCE-проверку в Redis (10 мин) и отвечает 307 на Keycloak `/auth` с `response_type=code`, `code_challenge` (PKCE S256), `state`, `nonce`.
2. Keycloak аутентифицирует (логин+пароль, для ADMIN и HEAD — TOTP), редиректит браузер на `GET /api/auth/callback?code=...&state=...` (есть и `POST /api/auth/callback` для программного обмена); после обмена backend ставит cookie `crm_sid` и `crm_csrf` и отвечает 303 на исходную страницу.
3. Backend сверяет `state`, обменивает `code` на `access_token` + `refresh_token` + `id_token` (client credentials конфиденциального клиента — секрет только на сервере).
4. Backend валидирует `id_token` (подпись по JWKS, `iss`, `aud`, `nonce`, `exp`), создаёт запись сессии в Redis: `session:{sid} → {user_id, tokens, ip, ua, created_at, last_seen}` с TTL = времени жизни refresh-токена. В браузер уходит только `sid` в httpOnly-cookie `crm_sid`.
5. Все запросы клиента идут на `/api/*` того же origin с cookie `crm_sid`; backend сам достаёт токен из сессии (отдельного прокси-слоя нет). CSRF закрывается `SameSite=Lax` + cookie `crm_csrf` и заголовком `X-CSRF-Token` на мутирующих методах.
6. FastAPI **не ходит в Keycloak на каждый запрос**: валидирует JWT локально по кэшированному JWKS (TTL 1 ч, принудительный refetch при неизвестном `kid`). Это критично для SLA — иначе каждый клик добавляет сетевой round-trip.
7. Первый запрос от нового пользователя триггерит **just-in-time provisioning**: если `sub` из токена нет в `users`, создаём локальную запись (см. §4.1).

Жизненные времена: `access_token` — 5 мин, `refresh_token` — 8 ч (рабочий день) с ротацией и reuse-detection, серверная сессия — до 12 ч, idle-таймаут — 30 мин.

## 3.2. Авторизация: RBAC + ABAC

Роли живут в Keycloak (`realm_access.roles`), но **решения о доступе принимает наш API**, потому что часть правил зависит от данных («КАМ видит только свои сделки») — IdP таких правил не знает.

Три слоя проверки, все обязательны:
1. **Роутинг** — декоратор `@require(Permission.DEAL_UPDATE)`: грубая отсечка по роли.
2. **Объектный уровень** — `policy.can(user, action, obj)`: проверяет ownership, команду, регион.
3. **Данные** — репозиторий всегда применяет `scope_filter(user)` к запросу списков. Это защита от IDOR: даже забытая проверка на уровне 2 не даст утечки в листингах.

Правила видимости:
- `KAM` — сделки, где он `owner_id` или состоит в `deal_participants`; организации, к которым привязана хотя бы одна его сделка; все справочники (read-only).
- `HEAD` (Руководитель) — всё в рамках своей команды (`team_id` подчинённых, рекурсивно по `teams.parent_id`); право `deal:reassign`.
- `ADMIN` — все права + конфигурация + управление доступами. Каждое чтение карточки сделки администратором пишется в аудит отдельным событием `PII_ACCESS` (`backend/app/modules/crm/router.py`).
- `INTEGRATION` (сервисная учётка) — узкий набор: создание сделок из входящего потока, обновление прогресса.
- `AUDITOR` — read-only доступ к журналу аудита и событиям безопасности, чтение соглашений ЭДО и карточек документов на подпись, чтение комментариев сделки через отдельную ручку (`comment:audit_read`); к самим сделкам доступа нет. Разделение обязанностей, чтобы админ не мог бесконтрольно чистить следы. Всего в `backend/app/core/permissions.py` 53 права на 5 ролей (`KAM`, `HEAD`, `ADMIN`, `AUDITOR`, `INTEGRATION`).

## 3.3. Аудит

Отдельная append-only таблица (§7.10). Пишется **в той же транзакции**, что и изменение — иначе возможно «изменил, но не залогировал». Реализация: сервис `AuditService.record(...)` вызывается явно из сервисного слоя в транзакции бизнес-операции и принимает diff изменённых полей (event-listener `after_flush` не используется); он никогда не коммитит сам.

Что фиксируем всегда: `actor_id`, `actor_role`, `impersonated_by` (если админ действовал от имени), `action`, `entity_type`, `entity_id`, `changes` (JSONB: `{field: [old, new]}`), `ip`, `user_agent`, `request_id`, `ts`, `result` (success/denied).

Чувствительные поля в `changes` маскируются: пароли не попадают никогда, персональные — по маске (`+7 (9**) ***-**-12`). **Отказы в доступе логируются тоже** — 403 без записи в лог означает, что попытку обхода прав никто не увидит.

Неизменяемость: у роли приложения есть `INSERT` и `SELECT` на `audit_log`, но нет `UPDATE`/`DELETE` (GRANT-уровень, а не «мы так договорились»). Дополнительно — цепочка хэшей: каждая запись хранит `prev_hash` и `hash`; при заданном `AUDIT_HMAC_KEY` хэш — HMAC-SHA256 (версия 3, без ключа — SHA-256, версия 2); голова цепочки — таблица `audit_chain_head` под advisory-локом; триггеры `BEFORE UPDATE/DELETE/TRUNCATE` стоят на каждой помесячной партиции; проверка — `GET /api/admin/audit/verify-chain`. Вырезание строки обнаруживается пересчётом цепочки.

## 3.4. Стратегия кэширования

Требование ТЗ — «кэш действий пользователя для быстрой загрузки ранее открытых карточек». Конкретно:

| Ключ | Что | TTL | Инвалидация |
|---|---|---|---|
| `cache:deal:{id}:v{version}` | Собранная карточка сделки (DTO) | 10 мин | Версионный ключ: при `UPDATE` инкрементится `deals.version` → старый ключ осиротел, читать некому |
| `cache:catalog:{type}:{hash}` | Справочники (продукты, направления, регионы) | 1 ч | Явный `DEL` по паттерну при изменении каталога |
| `cache:wf:{workflow_id}` | Граф статусов и переходов | 1 ч | Явный при публикации workflow |
| `cache:perm:{user_id}` | Развёрнутый набор прав | 5 мин | `DEL` при смене роли/команды, при logout, при удалении аккаунта |
| `recent:{user_id}` | ZSET последних 20 открытых сущностей — «кэш действий пользователя» в буквальном смысле ТЗ | — | LRU-подрезка |
| `lock:{resource}` | Redlock-подобный лок | 30 с | — |
| `idem:{key}` | Idempotency-результат | 24 ч | — |
| `rl:{ip}:{route}` | Счётчик rate-limit | окно | — |

Все ключи описаны в `backend/app/core/redis_client.py`; дополнительно используются `cache:kcid:{sub}` (соответствие субъекта токена пользователю), `cache:jwks` (TTL 1 ч) и другие служебные ключи. Принцип: **версионные ключи вместо инвалидации по событию** везде, где можно. Инвалидация — самая частая причина «призрачных» багов в CRM.

## 3.5. Конкурентный доступ

Два КАМа открыли одну сделку. Оптимистичная блокировка: `deals.version`, клиент шлёт `If-Match: "<version>"`, при несовпадении — `409 Conflict` с телом, содержащим актуальные значения конфликтующих полей, и UI показывает «поле изменено другим пользователем». Для перевода по статусу — дополнительно короткий Redis-лок на `deal:{id}:transition`, потому что двойной переход порождает двойной side-effect (две нотификации, две записи истории).

## 3.6. Идемпотентность и надёжность интеграций

Любой POST, порождающий сущность, принимает заголовок `Idempotency-Key`. Ключ + хэш тела → в Redis на 24 ч. Повтор возвращает сохранённый ответ, а не создаёт дубль. Обязательно для webhook'ов с сайта (Laravel будет ретраить) и для коннектора Bitrix.

Исходящие события — **transactional outbox**: в одной транзакции с бизнес-изменением пишем строку в `outbox_events`, отдельный воркер её вычитывает и доставляет с экспоненциальным backoff (1s, 5s, 30s, 5m, 30m, 2h), после 8 неудач — в `dead_letter` + алерт админу. Это гарантирует, что не бывает «сделка создана, но в Bitrix не уехала» и наоборот.

Входящие — **inbox**: сырое сообщение сохраняется целиком (`inbound_messages`) до разбора. Если парсер упал — сообщение не потеряно, можно переобработать после фикса. Дедупликация по `external_id + source`.

## 3.7. Работа с файлами

Загрузка **не проходит через API** — иначе один импорт на 50 МБ занимает воркер. Схема:
1. Клиент → `POST /api/files/upload-intent` с `{filename, size, mime, purpose}`. API валидирует лимиты, создаёт запись `files` в статусе `pending`, возвращает **presigned PUT URL** к SeaweedFS (TTL 15 мин).
2. Клиент грузит напрямую в S3.
3. Клиент → `POST /api/files/{id}/commit`. API проверяет фактическое наличие объекта, считает `sha256`, сверяет размер, ставит задачу антивирусной проверки, статус → `ready` (или `infected` → карантинный бакет + событие безопасности).
4. Скачивание — тоже presigned GET (TTL 5 мин), но **URL выдаётся только после проверки прав** на родительскую сущность.

Дедупликация по `sha256`: два одинаковых договора хранятся один раз, ссылок две. Важно для удаления аккаунта (§4.8): физически удалять объект можно только когда `refcount = 0`.

Валидация: whitelist MIME + проверка magic bytes (расширение врёт), запрет SVG (XSS), лимит 50 МБ/файл, 500 МБ/сделка.

## 3.8. Ошибки и контракт API

Единый формат — RFC 7807 Problem Details:
```
{"type":"/errors/workflow-transition-forbidden","title":"Переход недоступен",
 "status":422,"detail":"Из статуса «Согласование КП» нельзя перейти в «Запуск обучения»",
 "instance":"/api/deals/8f3.../transition","request_id":"01J...","errors":[...]}
```
Никогда не отдаём стектрейс наружу. **Реализовано:** `type` имеет вид `https://crm.rt-it-school.ru/problems/crm-xxyy`, в теле есть поле `code` из каталога `CRM-XXYY` (55 кодов с пояснением, `GET /api/meta/error-codes`). `request_id` — UUID, который Caddy кладёт в `X-Request-Id` (ULID не используется; клиентский заголовок сохраняется), он прокидывается через все слои и пишется в лог и в аудит — по нему за секунду находится вся цепочка.

## 3.9. Наблюдаемость

- Логи — JSON в stdout, поля `ts, level, request_id, user_id, module, msg`. **ПДн в логи не пишутся** — только ID.
- Метрики (`prometheus-client`, собственные метрики в `backend/app/core/metrics.py`; `/metrics` снаружи отдаёт 404, воркер — порт 9101): запросы по роутам, задачи arq, число сделок по состоянию SLA и др.; профиль compose `monitoring` (Prometheus + Grafana, `/grafana`). Hit-rate кэша и длина очереди как отдельные метрики — не проверено.
- Трассировка — OpenTelemetry **не реализована** (в зависимостях и коде её нет).
- Grafana-дашборд закрывает сразу два требования: мониторинг для нас и «интерактивные дашборды» из §5 ТЗ.

# ЧАСТЬ 4. ДЕТАЛЬНАЯ ПРОРАБОТКА СЦЕНАРИЕВ

Формат каждого: **что к этому приводит → что происходит → что следует за этим**. Это ядро задачи.

---

## 4.1. Появление пользователя в системе

**Принципиальное решение: самостоятельной регистрации нет.** Это внутренняя CRM с ПДн вузов; открытая регистрация — дыра. Registration в Keycloak-realm выключен.

**Что приводит:** приказ о приёме сотрудника / расширение команды → Администратор платформы создаёт учётку.

**Процесс:**
1. Админ в UI: `Администрирование → Пользователи → Создать`. Вводит ФИО, корпоративный email, роль, команду, руководителя.
2. API вызывает **Keycloak Admin API** (`POST /admin/realms/{realm}/users`) с `enabled=true`, `emailVerified=false`, без пароля, с `requiredActions: ["UPDATE_PASSWORD","VERIFY_EMAIL"]` (+ `CONFIGURE_TOTP`, если роль ADMIN или HEAD).
3. Keycloak возвращает `sub` (UUID). Создаём локальную `users` с `keycloak_id = sub`, `status = invited`.
4. Одноразовая ссылка — собственный токен приглашения (`user_invites`, в базе только хэш, TTL 72 ч), страница клиента `/invite/{token}`; пароль задаётся на ней и уходит в Keycloak.
5. Письмо с приглашением шлёт сам backend по SMTP (на стенде оно видно в Mailpit); канал Telegram — заглушка.

**Что следует:**
- Аудит: `USER_CREATED` с `actor_id` админа.
- Пользователь по ссылке задаёт пароль → Keycloak применяет политику (см. 4.4) → `status = active`.
- При первом входе — экран **согласия на обработку ПДн** (см. 4.2), без принятия дальше не пускаем.
- Если ссылка просрочена: `status` остаётся `invited`, админ жмёт «Отправить повторно» (rate-limit: не чаще 1/5 мин, не более 5/сутки).
- Если сотрудник так и не вошёл за 30 дней — автоматическое событие `USER_INVITE_EXPIRED`, учётка `disabled`, задача админу в уведомлениях.

**Edge cases:** email уже существует в Keycloak (возврат `409`, предложить «восстановить доступ» вместо создания); создание пользователя с ролью ADMIN требует подтверждения вторым админом (four-eyes) — сильный аргумент по ФСТЭК; создание при недоступном Keycloak → операция откатывается целиком, локальной записи-сироты не остаётся (сначала IdP, потом локальная БД, в одной SAGA с компенсацией).

## 4.2. Согласие на обработку ПДн

**Что приводит:** первый вход, либо изменение редакции политики.

**Процесс:** модальное окно с текстом политики и версией. Отказ = logout, доступа нет (для сотрудника — обоснованно: обработка его ПДн необходима для трудовых отношений, но фиксация факта ознакомления нужна).

**Что следует:** запись в `consents` (`user_id`, `policy_version`, `accepted_at`, `ip`, `user_agent`). При публикации новой версии политики флаг `consent_required` поднимается у всех, чья версия ниже — окно показывается снова. Это то, что реально проверяют при аудите 152-ФЗ, и это ровно одна таблица.

## 4.3. Вход, выход, управление сессиями

**Logout — три разных действия, и их часто путают:**

| Действие | Что делает | Где инициируется |
|---|---|---|
| Локальный выход | `DEL session:{sid}`, чистим cookie | Кнопка «Выйти» |
| Single Logout (SLO) | + `POST /protocol/openid-connect/logout` с `refresh_token` в Keycloak → завершаются сессии во всех приложениях realm | Та же кнопка, по умолчанию |
| Завершение всех сессий | Перебор `session:*` пользователя (индекс `user_sessions:{user_id}` — SET из sid) + Keycloak `logout-all` | Смена пароля, компрометация, действие админа |

**Back-channel logout:** Keycloak шлёт нам `POST /auth/backchannel-logout` с Logout Token. Обязателен — иначе админ «выкинул» пользователя в Keycloak, а наша Redis-сессия жива ещё 8 часов. Это типичная дыра в студенческих проектах, и её закрытие стоит отдельного упоминания на защите.

**Экран «Мои сессии»:** список активных (устройство, IP, гео-нет, последняя активность), кнопка «завершить». Данные — из `user_sessions:{user_id}`.

## 4.4. Смена пароля

Разбираем по трём разным входным ситуациям — они дают разные требования.

### Ситуация A. Добровольная смена (пользователь знает пароль)

**Что приводит:** личная гигиена, подозрение на утечку, требование регламента.

**Процесс:**
1. `Профиль → Безопасность → Сменить пароль`.
2. Форма: текущий пароль, новый, повтор. **Текущий обязателен** — иначе захваченная сессия = захваченный аккаунт навсегда.
3. Мы **не храним и не проверяем пароли сами**. Вариант реализации: редирект на Keycloak Account Console (`/realms/{r}/account/#/security/signingin`) — меньше кода, но UX «выкидывает» из нашего интерфейса. Выбранный вариант: собственная форма → BFF → Keycloak (проверка текущего пароля через grant `password` с полученными значениями, затем `PUT /admin/realms/{r}/users/{id}/reset-password` сервисной учёткой). Пароль **не логируется, не кэшируется, не попадает в аудит-changes**, живёт только в памяти запроса.
4. Политика (настраивается в realm `crm`, `deploy/keycloak/realm-crm.json`): `length(12)`, заглавная и строчная буквы, цифра, `notUsername`, `notEmail`, `passwordHistory(5)`. **Не реализовано:** проверка по словарю утёкших паролей и максимальный возраст 180 дней для ADMIN.

**Что следует — цепочка последствий (важнейшая часть):**
1. Keycloak инвалидирует все refresh-токены пользователя? **Нет, по умолчанию не инвалидирует.** Это ловушка. Мы делаем это явно: после успешной смены вызываем `logout-all` в Keycloak **и** удаляем все `session:*` пользователя, кроме текущей.
2. Текущая сессия переиздаётся с новым `sid` (защита от session fixation).
3. Событие безопасности `PASSWORD_CHANGED` → в `audit_log` (без значений!) и в `security_events`.
4. **Уведомление на email**: «Пароль изменён <дата>, IP <...>. Если это не вы — свяжитесь с администратором». Ссылка на самостоятельный «откат» не даётся (это вектор атаки) — только контакт админа.
5. `DEL cache:perm:{user_id}` — не потому что права изменились, а потому что после инцидента безопасности кэш должен пересобраться.
6. Сброс `requiredActions.UPDATE_PASSWORD`, если он был.
7. Инкремент `users.password_changed_at` — по нему считается принудительная ротация.
8. Если у пользователя были активные API-токены (сервисные интеграции) — они **не отзываются** (у них другой жизненный цикл), но в уведомление добавляется их список.

**Edge cases:** новый = текущему → `422` с явным текстом; 5 неудачных попыток ввода текущего пароля → временная блокировка формы на 15 мин и `security_event`; смена пароля во время фоновой задачи, запущенной этим пользователем, — задача не прерывается (она исполняется от сервисной учётки с сохранённым `initiated_by`).

### Ситуация B. Принудительная смена

**Что приводит:** (а) первый вход по приглашению; (б) сброс пароля админом; (в) истечение 180 дней для ADMIN; (г) реакция на инцидент.

**Процесс:** флаг `requiredActions: UPDATE_PASSWORD` в Keycloak. При следующем логине Keycloak сам не пускает дальше формы смены — нам не нужно ничего реализовывать, кроме корректной обработки редиректа. Наш API дополнительно отвергает любые запросы, если в токене присутствует claim о невыполненном required action (защита от обхода через прямой вызов API со старым access-токеном).

**Что следует:** то же, что в A, плюс `FORCED_PASSWORD_CHANGE` в аудите с указанием инициатора и причины.

### Ситуация C. Сброс забытого пароля

**Что приводит:** пользователь не помнит пароль.

**Процесс:**
1. Ссылка «Забыли пароль» на странице Keycloak (`Forgot password` включён в realm).
2. Ввод email → **всегда одинаковый ответ** «Если учётная запись существует, письмо отправлено» (защита от user enumeration).
3. Письмо с одноразовой ссылкой, TTL 15 мин.
4. Переход → форма нового пароля → та же политика.

**Что следует:** всё из A, **плюс обязательное завершение всех сессий без исключений** (включая текущую — пользователь логинится заново), плюс уведомление, плюс `security_event` с типом `PASSWORD_RESET`. Rate-limit 3 запроса на email/час и 10 на IP/час **не реализован** в backend: сценарий целиком на стороне Keycloak (форма «Забыли пароль», письмо на русском с темой `rtk-crm`, ссылка живёт 15 минут — `actionTokenGeneratedByUserLifespan=900`); сброс паролем по инициативе администратора (сценарий B) реализован полностью и пишет `PASSWORD_RESET`.

**Граничный случай:** если атакующий имеет доступ к почте, сброс пароля = полный захват. Митигация — для ролей HEAD и ADMIN при создании учётки назначается обязательное действие `CONFIGURE_TOTP`, тогда сброс пароля сам по себе доступа не даёт.

## 4.5. Блокировка и разблокировка учётной записи

**Что приводит:** отпуск/декрет, подозрение на компрометацию, отстранение, автоматика (5 неудачных логинов подряд — `failureFactor` — → Keycloak brute-force detection, временная блокировка с ростом до 15 мин, `maxFailureWaitSeconds=900`).

**Процесс:** админ → `disabled=true` в Keycloak + `users.status = blocked` локально + причина (обязательное поле) + опционально дата авторазблокировки.

**Что следует:**
- Немедленное завершение всех сессий (иначе он работает ещё 8 часов).
- Сделки **не переназначаются автоматически** — это отличие от увольнения. Они остаются за ним, но помечаются `owner_unavailable = true`; руководитель видит их в отдельном фильтре «Требуют внимания».
- Если блокировка длится > 14 дней — автоматическое напоминание руководителю о переназначении.
- Уведомления, адресованные заблокированному, не доставляются ему, а эскалируются руководителю.
- Аудит `USER_BLOCKED` + причина.

**Разблокировка:** `status = active`, сессии не восстанавливаются (логин заново), `owner_unavailable` снимается, аудит.

## 4.6. Смена роли и перевод между командами

**Что приводит:** повышение КАМ→Руководитель, переход в другой отдел.

**Процесс:** админ меняет роль → обновляются role mappings в Keycloak **и** `users.role` локально (денормализация для скорости фильтрации, синхронизируется односторонне: Keycloak — источник истины, при рассинхроне побеждает токен).

**Что следует — здесь много неочевидного:**
- `DEL cache:perm:{user_id}` немедленно.
- Уже выданный access-токен содержит **старые** роли и живёт ещё до 5 минут. Для понижения прав это неприемлемо. Решение: `users.perm_epoch` (счётчик); эпоха из токена сверяется с эпохой в кэше принципала, и запись с устаревшей эпохой не берётся из кэша, а проверяется по БД (`backend/app/core/deps.py`). Отдельного ответа `401 token_stale` и «тихого refresh» в коде нет.
- При понижении KAM←HEAD: доступ к сделкам подчинённых теряется, но он остаётся `owner` своих — данные не осиротеют.
- При повышении KAM→HEAD: нужно указать, какую команду он возглавляет, иначе роль бессмысленна — валидация на уровне API.
- Если из системы уходит **последний ADMIN** — операция блокируется (`422 last_admin`). Это правило действует и при блокировке, и при удалении (код ошибки `CRM-1903`).
- Аудит `ROLE_CHANGED` с `[old, new]`.

## 4.7. Увольнение сотрудника (offboarding)

Отдельный сценарий, потому что это не «удаление аккаунта» — данные компании должны остаться.

**Что приводит:** увольнение, окончание договора.

**Процесс — мастер из 4 шагов, а не одна кнопка:**
1. Админ/руководитель запускает «Передача дел». Система показывает всё, что держит уходящий: N сделок (по статусам), M задач, K подписок на уведомления, активные импорты/отчёты.
2. Выбор преемника — одного на всё или по-сделочно (bulk с фильтрами).
3. Предпросмотр: «Будет переназначено 34 сделки на Иванова, 3 сделки в статусе «Подписание договора» — отдельно выделены как критичные».
4. Подтверждение → атомарная транзакция: `deals.owner_id` меняется, в `deal_status_history` **не пишется** (статус не менялся), но пишется `deal_events` типа `OWNER_CHANGED`; в каждую сделку добавляется системный комментарий «Ответственный изменён: Петров → Иванов (причина: увольнение)».

**Что следует:**
- Учётка → `status = terminated`, `disabled` в Keycloak, все сессии завершены.
- Комментарии, файлы, история — **остаются с авторством**. Уходящий сотрудник не имеет права требовать их удаления: это не его ПДн, а деловая переписка компании.
- ПДн самого сотрудника (телефон, личный email) обезличиваются по истечении установленного срока хранения (см. 4.8, режим B).
- Преемник получает уведомление со списком принятых сделок.
- Аудит: `USER_TERMINATED` + `BULK_REASSIGN` с полным списком ID.

## 4.8. Удаление аккаунта — полный разбор

Самый недооценённый сценарий. Ошибка здесь = либо потеря корпоративных данных, либо нарушение 152-ФЗ.

### 4.8.1. Что вообще приводит к удалению

| Триггер | Кто инициирует | Применимый режим |
|---|---|---|
| Увольнение | Админ | B (обезличивание) после срока хранения |
| Ошибочно созданная учётка, которая ни разу не входила | Админ | C (жёсткое удаление) — данных нет |
| Отзыв согласия на обработку ПДн субъектом (ст. 9 152-ФЗ) | Субъект ПДн (контакт B2C, представитель вуза) | B — обязательно, срок 30 дней |
| Требование субъекта об уничтожении ПДн (ст. 21) | Субъект | B, срок 7 рабочих дней |
| Истечение срока хранения / достижение цели обработки | Автоматика (ретеншен-политика) | B |
| Компрометация сервисной учётки | Админ | C |

**Критично: «удаление аккаунта сотрудника» и «удаление ПДн контакта» — два разных процесса.** Их смешивание — главная архитектурная ошибка в подобных системах. Сотрудник — субъект `users`, контакт — субъект `contacts`. Ниже описаны оба.

### 4.8.2. Три режима удаления

**Режим A — Деактивация (soft delete).** `status = disabled`, `deleted_at = now()`. Данные целы, вход закрыт. Обратимо. Используется как **обязательный первый шаг** любого удаления: grace period 30 дней.

**Режим B — Обезличивание (анонимизация).** Запись `users`/`contacts` физически остаётся (на неё ссылаются десятки FK), но все персональные поля затираются:
- `full_name` → `Пользователь #4821` (стабильный псевдоним из `id`, не «Удалён» — иначе в истории 15 одинаковых «Удалён» и отчёты ломаются);
- `email` → `deleted-4821@anonymized.local`, `phone` → `NULL`, `avatar_file_id` → `NULL` (файл в S3 удаляется, если refcount=0);
- `keycloak_id` → `NULL`, учётка в Keycloak удаляется физически;
- `anonymized_at = now()`, `status = anonymized`.
Бизнес-факты сохраняются: «сделка была создана пользователем #4821 12.03.2026» — это не ПДн, это операционная история, необходимая для отчётности и требуемая законом о бухучёте.

**Режим C — Жёсткое удаление (hard delete).** Физический `DELETE`. Разрешён **только** если у сущности нет ни одной зависимой записи (проверяется явным подсчётом, а не надеждой на `ON DELETE`). Практически применим только к учёткам, которые никогда не использовались.

### 4.8.3. Каскад: что происходит с каждой связанной сущностью

Это главная таблица раздела. Для каждой связи задан явный `ON DELETE`-контракт, и ни одна не использует `CASCADE` — каскадное удаление в CRM недопустимо, оно молча уничтожает историю.

| Связанная сущность | Поведение при обезличивании пользователя | Обоснование |
|---|---|---|
| `deals.owner_id` | **Блокирующая проверка.** Удаление невозможно, пока есть активные сделки. Требует предварительной передачи (4.7) | Сделка без ответственного — потерянные деньги |
| `deals.created_by` | Остаётся, FK `ON DELETE RESTRICT`, ссылается на обезличенную запись | История создания — операционный факт |
| `deal_comments.author_id` | Остаётся. Текст комментария **не удаляется**, но сканируется на наличие ПДн автора (подпись «— Иван, +7...») и при отзыве согласия маскируется | Деловая переписка принадлежит компании |
| `deal_status_history.changed_by` | Остаётся | Аудит воронки, нужен для отчётов |
| `attachments.uploaded_by` | Остаётся. Сами файлы — по признаку `contains_pd`: рабочие документы остаются, персональные (скан паспорта) удаляются из S3 | — |
| `audit_log.actor_id` | **Не изменяется никогда.** Ссылается на ID, который теперь обезличен | Аудит-лог immutable по определению; ФСТЭК требует сохранности следов |
| `tasks.assignee_id` | Открытые → переназначаются руководителю, закрытые → остаются | — |
| `notifications` (адресованные) | Непрочитанные удаляются, доставленные — остаются как факты в `notification_deliveries` без тела | — |
| `user_sessions` (Redis) | Удаляются немедленно | — |
| `report_jobs.requested_by` | Остаётся; готовые отчёты, содержащие ПДн этого пользователя, помечаются к перегенерации | Отчёт — тоже носитель ПДн, про это забывают |
| `outbox_events` с его данными | Неотправленные — отменяются; отправленные — фиксируются как переданные третьим лицам (нужно для реестра трансграничной/сторонней передачи) | 152-ФЗ требует знать, кому передали |
| Внешние системы (Bitrix, LMS) | Отдельное событие `ERASURE_REQUESTED` в коннектор — обязанность уведомить об уничтожении распространяется на всех, кому передавали | Ст. 21 ч. 4 152-ФЗ |
| `files` (S3) | `refcount--`; физическое удаление объекта только при `refcount = 0`, + версия в корзине SeaweedFS на 30 дней | Дедупликация не должна приводить к удалению чужого файла |

> **Реализовано частично.** Каскад выполнен для сделок, задач, ожидающих запросов на подпись, учётной записи Keycloak, аватара и внешних систем (событие `ERASURE_REQUESTED` уходит через outbox). Очистка уведомлений, пометка отчётов на перегенерацию и обработка вложений с признаком `contains_pd` предусмотрены схемой БД, но не подключены к исполнению удаления (`backend/app/modules/identity/erasure_service.py`). Обезличивание сохраняет подписи (`dop.md`, §10.7). Отсрочка режима A — 30 дней (`ERASURE_GRACE_DAYS`), подтверждение двумя администраторами — таблица `admin_approvals`, акт об уничтожении — PDF (миграция 0035).

### 4.8.4. Процесс — пошагово

1. **Инициация.** Создаётся запись `data_erasure_requests` (`subject_type`, `subject_id`, `reason`, `requested_by`, `legal_basis`, `deadline_at`). Для запроса от субъекта дедлайн считается автоматически (30 дней / 7 рабочих дней).
2. **Проверка блокеров.** Синхронный отчёт: активные сделки, незакрытые задачи, является ли последним админом, есть ли юридические основания отказать (например, данные нужны для исполнения действующего договора — законное основание отказать в удалении, и система должна позволять это зафиксировать).
3. **Разрешение блокеров.** Мастер передачи дел (4.7).
4. **Grace period.** Режим A на 30 дней. Все дни учётка видна в `Администрирование → Удаляемые` с обратным отсчётом и кнопкой «Восстановить».
5. **Исполнение.** Фоновая задача, транзакционно, по шагам с чекпоинтами (задача может упасть на шаге 6 из 11 — должна продолжиться, а не начаться заново):
   - удаление в Keycloak → затирание полей → удаление файлов → отмена outbox → публикация `ERASURE_REQUESTED` внешним → маскирование в отчётах → запись результата.
6. **Подтверждение.** Генерируется акт об уничтожении ПДн (PDF) с перечнем категорий данных, датой, ответственным. Это документ, который заказчик обязан предъявить при проверке Роскомнадзора. Хранится в S3 бессрочно.
7. **Финал.** `data_erasure_requests.status = completed`, аудит `USER_ANONYMIZED` / `SUBJECT_ERASED`.

### 4.8.5. Особый случай — удаление контакта (B2C, субъект ПДн)

Отличия от сотрудника:
- Инициатор — сам субъект (через форму на сайте → webhook → создаётся `data_erasure_request`) или оператор по его письменному обращению.
- Нет «передачи дел», но есть проверка: если контакт связан с **действующим** договором на обучение, обработка ПДн остаётся законной до окончания договора + срок хранения (обычно 5 лет для документов). Система обязана уметь **обоснованно отклонить** запрос со ссылкой на основание — и зафиксировать это.
- После обезличивания сделка остаётся в статистике («в 2026 г. обработано 480 B2C-заявок»), но без возможности идентифицировать человека. Это и есть корректная анонимизация: агрегат сохранён, субъект неидентифицируем.
- Сложный момент, который надо предусмотреть: **повторное появление**. Человек удалился, через год подал заявку снова. Дедупликация по email/телефону невозможна (их нет). Значит, появляется новый контакт — и это правильное поведение, а не баг. В UI не должно быть попыток «склеить».

### 4.8.6. Чего система делать НЕ должна

- Не удалять записи аудита ни при каких условиях, включая запрос субъекта. Аудит-лог хранит `actor_id`, а не ПДн; законное основание — обеспечение безопасности ИСПДн.
- Не давать администратору кнопку «удалить всё немедленно» в обход grace period — только через два подтверждения разных админов.
- Не позволять удалить собственную учётку администратору (самоблокировка системы).

## 4.9. Жизненный цикл сделки

**Создание.** Источники: (1) ручной ввод КАМ, (2) webhook с сайта (B2C), (3) импорт, (4) коннектор Bitrix, (5) конвертация из входящего обращения. При создании: определяется `workflow_id` по `deal_type` + текущей опубликованной версии, `status_id` = `initial`-статус, `owner_id` (правило назначения: ручной выбор / round-robin внутри команды / по региону организации), пишется `deal_events: CREATED`.

**Переход по статусу — центральная операция, под SLA в 1 секунду.**
Последовательность (целевой бюджет 300 мс):
1. Загрузка сделки + версия (кэш или БД) — 5 мс.
2. Проверка `If-Match` — 0 мс.
3. Проверка: существует ли `transition` из текущего в целевой в опубликованной версии workflow (граф из кэша) — 1 мс.
4. Проверка прав на этот конкретный переход (`transitions.allowed_roles`) — 1 мс.
5. Проверка **guard-условий**: обязательные поля заполнены, обязательные вложения приложены, дочерние задачи закрыты. Условия хранятся декларативно в `transitions.conditions` (JSONB) — DSL вида `{"all":[{"field":"contract_file_id","op":"not_null"},{"field":"amount","op":">","value":0}]}`. Не код, иначе конструктор workflow превращается в фикцию.
6. Транзакция: `UPDATE deals SET status_id, version+1, status_changed_at` + `INSERT deal_status_history` + `INSERT audit_log` + `INSERT outbox_events` + пересчёт SLA-дедлайна — 15 мс.
7. Коммит. Ответ клиенту. **Всё тяжёлое — после:** уведомления, синхронизация в Bitrix, пересчёт дашбордов уходят в очередь.

**Постэффекты (асинхронно):** уведомление новому ответственному и руководителю (если статус критичный), запуск SLA-таймера, автосоздание задач (`transitions.actions`: «при входе в «Согласование КП» создать задачу юристу с дедлайном +3 дня»), отправка события во внешние системы.

**Откат назад.** Разрешён, если в графе есть обратное ребро. Обратный переход всегда требует комментария с причиной — иначе воронка перестаёт быть источником правды для аналитики.

**Закрытие.** `won` — обязательны сумма и дата; `lost` — обязательна причина из справочника `loss_reasons` + свободный комментарий. Без справочника причин отчёт «почему мы теряем вузы» невозможен, а это главный отчёт руководителя.

## 4.10. SLA и эскалации

**Что приводит:** сделка «зависла» — требование ТЗ про 1–2 недели.

**Механика:** `sla_rules` привязаны к паре (workflow, status): `max_duration`, `warn_at` (%), `escalate_to` (роль/конкретный пользователь), `channels`. При входе в статус вычисляется `sla_due_at` **в рабочих днях** с учётом производственного календаря (справочник `holidays`) — иначе новогодние каникулы порождают вал ложных эскалаций.

Cron-воркер раз в 15 минут выбирает `WHERE sla_due_at < now() AND sla_state != 'breached'` (индекс частичный, только по незакрытым сделкам — запрос остаётся быстрым при любом объёме). Ступени: 75% времени → напоминание КАМу; 100% → уведомление КАМу + руководителю, сделка помечается флагом в интерфейсе; 150% → эскалация на уровень выше + попадание в отчёт «Проблемные сделки».

**Пауза SLA:** статус типа `parked` (ждём ответа вуза) таймер останавливает, накопленное время сохраняется. Без этого механизма КАМы начнут «прятать» сделки в неподходящие статусы, и данные испортятся.

## 4.11. Конструктор workflow и сопоставление статусов

Требование ТЗ, самое сложное место.

**Создание/редактирование.** Визуальный редактор графа (`@xyflow/svelte`): узлы-статусы, рёбра-переходы. Для каждого узла: название, тип, цвет, обязательные поля, SLA. Для ребра: разрешённые роли, условия, действия.

**Версионирование.** ТЗ говорит «версионирование не требуется, изменения применяются ко всем». Принимаем, но с оговоркой: у workflow есть `draft` и `published` состояния. Редактирование идёт в черновике, публикация — атомарная операция с валидацией. Это не версионирование сущностей, это защита от публикации полуготового графа — и её отсутствие убьёт демо, если кто-то начнёт править воронку при живых пользователях.

**Валидация перед публикацией (блокирующая):**
- ровно один статус типа `initial`;
- минимум один терминальный;
- нет недостижимых статусов (обход графа из initial);
- нет статусов, из которых нельзя попасть ни в один терминальный («ловушки»);
- все `conditions` ссылаются на существующие поля.

**Удаление/изменение статуса — процедура сопоставления.** Требование ТЗ в чистом виде.
1. Пользователь удаляет статус «Согласование КП», в котором висит 27 сделок.
2. Система **блокирует** удаление и открывает мастер сопоставления: «27 сделок нужно перенести. Куда?»
3. Выбор целевого статуса (один для всех или правилами: по типу сделки / по сумме).
4. Предпросмотр: сколько сделок, какие именно, что будет с их SLA-таймерами (сбросить / сохранить / пересчитать), какие обязательные поля целевого статуса у них не заполнены (список проблемных сделок — им нужен отдельный fallback-статус).
5. Подтверждение → фоновая задача батчами по 100: перевод статуса, запись в `deal_status_history` с `reason = 'workflow_migration'` и ссылкой на `status_mapping_job`, системный комментарий в каждую сделку.
6. Только после успешного завершения статус помечается `archived` (не удаляется физически — на него ссылается история).

**Ключевой принцип:** статусы никогда не удаляются из БД, только архивируются. `deal_status_history` должна оставаться читаемой через год.

## 4.12. Импорт каталогов (.xls / .xlsx)

**Что приводит:** заказчик присылает реестр из 500 вузов в Excel.

**Процесс — 5 фаз, каждая обратима:**
1. **Загрузка** — presigned PUT, запись `import_jobs` в статусе `uploaded`.
2. **Разбор и профилирование.** Читаем **первые 100 строк** для превью. `xlsx` → openpyxl в `read_only` режиме (иначе файл на 50 МБ съедает 2 ГБ RAM); `xls` → `xlrd`; `csv` → детект кодировки через `charset-normalizer` (требование ТЗ про «слетевшие кодировки»: CP1251 и UTF-8-BOM обязательны) и детект разделителя (`;` — стандарт русского Excel). Защита от «битых»: обёртка в try/except с конкретными сообщениями, лимит 50 МБ / 100 000 строк, проверка magic bytes, защита от zip-bomb в xlsx, **запрет формул** (CSV-инъекция: ячейка `=cmd|'/c calc'!A1`).
3. **Маппинг** — требование ТЗ про диалоговое окно. Слева колонки файла с примерами значений, справа поля системы. Автоподбор по нечёткому совпадению имён (Левенштейн + словарь синонимов: «Наименование» → `name`, «ИНН» → `inn`). Маппинг сохраняется как `import_presets` — второй импорт того же реестра не требует ручной работы.
4. **Валидация (dry-run).** Прогон всех строк без записи: типы, обязательность, форматы (ИНН — 10/12 цифр с контрольной суммой, email — RFC, телефон — нормализация к E.164), дубли внутри файла, коллизии с БД. Результат — отчёт: X ок, Y с предупреждениями, Z с ошибками + скачиваемый .xlsx с исходными строками и колонкой «Причина ошибки». Это то, что превращает импорт из мучения в инструмент.
5. **Применение.** Стратегия на выбор: `insert only` / `upsert` по ключу (`inn` для вузов) / `update only`. Батчами по 500 в отдельных транзакциях с чекпоинтом. Ошибочные строки — пропускаются, не откатывают весь импорт. По завершении — `import_jobs.status = completed`, статистика, **кнопка «Откатить импорт»** (по `import_job_id` помеченные записи, созданные этим импортом, можно снять; изменённые — восстановить из сохранённого снапшота `before` в `import_row_results`).

## 4.13. Отчётность и экспорт

Форматы по ТЗ: `.xls/.xlsx/.pdf` для отчётов, `.png/.pdf` для графиков.

**Базовый набор отчётов:** воронка по статусам (конверсия и время между шагами), сводка по КАМам, по регионам/вузам, причины отказов, соблюдение SLA, динамика по месяцам, прогресс обучения (из LMS), «зависшие сделки».

**Архитектура выполнения.** Требование «10 параллельных отчётов» — это про очередь, а не про синхронные запросы. Синхронно отдаём только «лёгкие» отчёты (< 1 000 строк, < 2 с). Тяжёлые: `POST /reports` → `report_job` в очередь → SSE/поллинг статуса → готовый файл в S3 → presigned ссылка + уведомление. Конкурентность воркеров ограничена семафором (`REPORTS_MAX_CONCURRENT=10`), очередь длиннее — задачи ждут, а не роняют БД; отдельного нагрузочного прогона «10 параллельных тяжёлых отчётов» не было — не проверено.

**Технически:** xlsx — `openpyxl` в `write_only` (стриминг, константная память); pdf — HTML-шаблон (Jinja2) → `xhtml2pdf` (вместо WeasyPrint, который требует системных библиотек) со шрифтом DejaVu Sans для кириллицы; png графиков — серверный matplotlib (не скриншот фронта — на сервере нет браузера, и это типичная ловушка).

**Безопасность отчётов, о которой забывают:** отчёт — это выгрузка ПДн. Поэтому: (а) содержимое отчёта фильтруется правами заказчика (КАМ не выгружает чужие сделки); (б) каждая генерация — событие `REPORT_EXPORTED` в аудите с указанием количества строк и категорий данных; (в) presigned-ссылка живёт 15 минут (`REPORTS_LINK_TTL_MINUTES`; одноразовость не проверялась); (г) готовые файлы автоудаляются через 7 дней (`REPORTS_RETENTION_DAYS`).

**Дашборды.** Внутренние (свои, на Svelte; графики — `@lct-testkit/rt-ui/charts`, не uPlot) + Grafana-дашборд мониторинга (профиль `monitoring`). Кэш агрегатов в Redis на 5 минут + материализованные представления PostgreSQL с `REFRESH CONCURRENTLY` по расписанию — это то, что даёт мгновенный дашборд вместо 20-секундного ожидания.

## 4.14. Интеграции на заглушках

**Сайт (Laravel CMS):** входящий webhook `POST /api/v1/integrations/cms/leads` с HMAC-SHA256 подписью в заголовке и `Idempotency-Key`. Сырое тело → `inbound_messages` → разбор → создание `contact` + `deal` в B2C-workflow.

**LMS:** исходящий pull по cron (каждые 30 мин) `GET /api/students/progress?updated_since=...` с курсором в `sync_cursors`. Данные → `learning_progress`. Отдельно — push статусов зачисления в LMS при переходе сделки в «Запуск обучения».

**Что сделано:** **контракты** лежат как OpenAPI 3.1 файлы `deploy/mocks/cms/openapi.yaml` и `deploy/mocks/lms/openapi.yaml` (каталога `contracts/` нет), из них поднимаются мок-серверы на Prism (профиль compose `integrations`); клиента из них никто не генерирует — клиентский код интеграций написан вручную. Когда заказчик даст реальные контракты — меняется один YAML и базовый URL, код интеграции не трогается. Это ровно то, о чём просили менторы, и это демонстрируемо: на защите переключаем `LMS_BASE_URL` с мока на «реальный» — и всё работает.

**Bitrix24-коннектор.** Не отдельный контейнер, а модуль `integration` (`backend/app/modules/integration/bitrix.py`), работает через `outbox_events` и таблицу `external_refs`; включается `BITRIX_CONNECTOR_ENABLED` (по умолчанию выключен) и источником `bitrix24` в `integration_sources`. **Реализовано:** создание и обновление сделки в Bitrix24 (`crm.item.add`/`crm.item.update`, прогон на живом портале 25.09.2026 — см. README, «Интеграция с Битрикс24»). **Не реализовано:** двусторонняя синхронизация с правилом last-write-wins и `synced_version`, журнал расхождений, перенос статуса из Bitrix; входящий `POST /api/v1/integrations/bitrix/webhook` принимает упрощённый собственный контракт с HMAC-подписью, настоящая подписка на события Bitrix (`event.bind`) не поднята. Ядро про Bitrix не знает: коннектор отключается флагом.

# ЧАСТЬ 6. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

**Производительность.** Бюджет 1 секунды на действие: сеть 100 мс + SSR/BFF 50 мс + API 300 мс (p95) + рендер 150 мс + запас 400 мс. Правила, обеспечивающие бюджет: обязательная пагинация (cursor-based по `(created_at, id)`, не OFFSET — на 50 000 сделок OFFSET деградирует), запрет N+1 (`selectinload` явно, тест на количество запросов в CI), индексы под каждый фильтр списка, всё тяжёлое — в очередь.

**План нагрузочного тестирования** (требование ТЗ: приложить результаты). Исходный план — k6 с пятью профилями; **сделано иначе:** инструмент — Locust (`backend/loadtest/`), два сценария (комментарий и переход по статусу) с гейтом `assert_slo.py` (p95 ≤ 300 мс, ошибок ≤ 1 %, RPS ≥ 90 % цели) при 50 RPS; workflow `loadtest.yml` запускается вручную (ночной запуск отключён: у организации не работает биллинг GitHub Actions). Профили Smoke, Reports, Stress и Soak не выполнялись. Исходный план:
1. Smoke — 1 VU, 1 мин, проверка работоспособности.
2. Load — 50 VU, 10 мин, реалистичный микс: 60% чтение списков/карточек, 25% переходы по статусам, 10% комментарии, 5% создание. Критерий: `http_req_duration p95 < 500ms`, `http_req_failed < 1%`.
3. Reports — 10 параллельных генераций тяжёлых отчётов на фоне Load-профиля. Критерий: интерактивные запросы не деградируют выше p95 800 мс (то есть очередь отчётов действительно изолирует).
4. Stress — рост до отказа, фиксируем точку деградации (ожидаем 200–400 VU).
5. Soak — 30 VU на 2 часа, ловим утечки памяти и рост connection pool.

**Масштабирование до 300+ пользователей** (описывалось в документации, не реализовывалось; из перечня сделаны горизонтальные реплики `api` за Caddy и кластер PostgreSQL на Patroni с репликами, есть Helm-чарт `deploy/charts/rtk-crm` — его установка в реальный кластер не проверялась; PgBouncer, read-реплика для отчётов, Redis Sentinel и HPA не делались): горизонтальное масштабирование stateless-контейнеров `api`/`web` за Caddy (сессии уже в Redis — узла состояния нет); PgBouncer в режиме transaction перед PostgreSQL; read-реплика для отчётов и дашбордов; вынос `reporting` и `integration` в отдельные сервисы (модульный монолит это позволяет без переписывания); партиционирование `deals` по годам и `audit_log` по месяцам; Redis Sentinel; переезд compose → k3s с HPA по CPU и длине очереди.

**Доступность.** Целевой RTO 4 ч, RPO 15 мин. **Реализовано:** `deploy/scripts/backup.sh` (роли кластера, базы `crm` и `keycloak`, том SeaweedFS, контрольные суммы) и `deploy/scripts/restore_test.sh`, который поднимает чистый стенд из бэкапа и гоняет smoke (ночью то же делает `e2e.yml`) — вместо `make restore-test`. **Не реализовано:** WAL-архивирование, поэтому при ежедневном дампе RPO по факту — сутки; бэкапов по расписанию в HA-конфигурации нет; экспорт realm при каждом изменении не делается (realm берётся из `realm-crm.json`). Непроверенный бэкап не существует.

**Безопасность (152-ФЗ + приказ ФСТЭК № 117, конкретика, а не декларации):**
- Идентификация и аутентификация — Keycloak, парольная политика, TOTP для привилегированных.
- Управление доступом — RBAC+ABAC, принцип минимальных привилегий, разделение ролей администратора и аудитора.
- Регистрация событий — аудит-лог с цепочкой хэшей, неизменяемость на уровне GRANT и триггеров, помесячное партиционирование; срок хранения событий безопасности — 36 месяцев (`RETENTION_SECURITY_EVENTS_MONTHS`), срок хранения самого аудита — не проверено.
- Защита при передаче — TLS 1.3, HSTS, внутренний трафик в изолированных docker-сетях.
- Защита при хранении — шифрование на уровне полей в приложении (Fernet, ключ `FIELD_ENCRYPTION_KEY` с ротацией `_PREV`) для СНИЛС, паспорта и адреса учащегося; телефоны и e-mail контактов в базе открытым текстом, при выдаче маскируются (раскрытие — отдельное право и событие аудита). Шифрование томов на уровне ОС (LUKS) в документации по развёртыванию не описано — не реализовано.
- Обезличивание — реализовано механикой §4.8, плюс генератор обезличенного дампа для dev-среды (**на тестовых стендах реальные ПДн не появляются никогда** — отдельный пункт, который ценят на защите).
- Целостность — контроль `sha256` файлов, миграции только через Alembic.
- Антивирус — клиент ClamAV (`CLAMAV_ENABLED`, по умолчанию выключен: работает заглушка); сервиса ClamAV в `docker-compose` и в `images.yaml` нет, а переменные `CLAMAV_*` не входят в `x-api-env` — включить сканер можно только правкой compose и отдельным сервисом.
- Управление уязвимостями — `pip-audit` (с `--require-hashes`) и Trivy по образам в CI backend, gitleaks по истории; зафиксированные версии зависимостей (lock-файлы), digest-пиннинг образов (`deploy/images.yaml`, `FROM ...@sha256`). `npm audit` для клиента — не проверено.
- Реагирование — `security_events` (журнал и сводка в панели безопасности администратора) и реестр инцидентов ПДн со сроками РКН 24/72 ч; алерты в Telegram не реализованы (канал — заглушка).
- Организационные документы (шаблоны в репозитории `backend`, `docs/security/org/`): политика обработки ПДн, перечень ПДн, модель угроз, приказ о назначении ответственного, акт об уничтожении (ручной).

**Документация в платформе** (требование ТЗ): раздел `/help` с руководством пользователя и администратора, markdown-исходники в репозитории, рендер при сборке, скриншоты генерируются автоматически из Playwright-тестов — значит, не устаревают.

> **Сверка с кодом.** Все таблицы частей 7 и dop.md (10–11) есть в моделях `backend/app/modules/*/models.py` (76 моделей, 53 миграции Alembic, `0001`–`0053`); добавлены таблицы, которых здесь нет: `access_requests`, `admin_approvals`, `api_keys`, `audit_chain_head`, `contact_learner_profiles`, `contact_products`, `organization_licenses`, `retention_runs`, `security_incidents`, `signature_download_links`, `user_access_rules`, `user_invites`, `webhook_subscriptions`, `webhook_deliveries`. **`integration_sources`** — `id, code ('cms','lms','bitrix24'), name, base_url, auth_type, credentials_ref text (ссылка на секрет, НЕ сам секрет), is_active, config jsonb, last_sync_at, last_error`.

**`inbound_messages`** — `id, source_code, external_id, message_type, raw_payload jsonb, signature_valid bool, status ('received','processed','failed','duplicate'), error, processed_at, received_at`. `UNIQUE(source_code, external_id)` — дедупликация на уровне БД.

**`outbox_events`** — `id, aggregate_type, aggregate_id, event_type, payload jsonb, target text, status ('pending','sent','failed','dead'), attempts int, next_retry_at, last_error, created_at, sent_at`. Индекс `(status, next_retry_at) WHERE status IN ('pending','failed')`.

**`external_refs`** — `id, entity_type, entity_id, source_code, external_id, synced_version int, last_synced_at, sync_direction`. `UNIQUE(source_code, entity_type, external_id)` и `UNIQUE(source_code, entity_type, entity_id)` — двусторонняя однозначность.

**`sync_cursors`** — `id, source_code, resource, cursor_value, updated_at`.

**`learning_progress`** — данные из LMS: `id, contact_id, deal_id, product_id, external_course_id, enrolled_at, progress_pct, score, completed_at, last_activity_at, raw jsonb, synced_at`.

## 7.9. Домен: Импорт и отчёты

**`import_jobs`** — `id, file_id, entity_type, mode ('insert','upsert','update'), mapping jsonb, status, total_rows, ok_rows, warn_rows, error_rows, result_file_id, initiated_by, started_at, finished_at, rollback_available bool, rolled_back_at`.

**`import_row_results`** — `id, import_job_id, row_number, status, entity_id NULL, before_snapshot jsonb, errors jsonb`. Хранение `before_snapshot` — то, что делает откат импорта возможным.

**`import_presets`** — `id, name, entity_type, mapping jsonb, created_by, created_at`.

**`report_templates`** — `id, code, name, description, query_def jsonb, allowed_roles text[], default_params jsonb, output_formats text[]`.

**`report_jobs`** — `id, template_code, params jsonb, format, requested_by, status, progress_pct, row_count, file_id, error, expires_at, created_at, finished_at`.

**`dashboards` / `dashboard_widgets`** — `id, name, owner_id, is_shared, layout jsonb` / `id, dashboard_id, widget_type, config jsonb, position`.

## 7.10. Домен: Аудит и система

**`audit_log`** — партиционирована по `created_at` (RANGE, помесячно).
```
id uuid PK (part of composite with created_at)
created_at timestamptz NOT NULL
actor_id uuid NULL                     -- без FK: ссылка переживает удаление
actor_role text
impersonated_by uuid NULL
action text NOT NULL                   -- 'DEAL_STATUS_CHANGED','USER_ANONYMIZED',...
entity_type text, entity_id uuid
changes jsonb                          -- {"status_id":["old","new"]}, ПДн замаскированы
result text CHECK (result IN ('success','denied','error'))
ip inet, user_agent text, request_id text
prev_hash text, hash text              -- цепочка целостности
```
Индексы: `(entity_type, entity_id, created_at DESC)`, `(actor_id, created_at DESC)`, `(action, created_at DESC)`, GIN по `changes`. Права: роль приложения — только `INSERT`/`SELECT`.

**`feature_flags`** — `id, code, is_enabled, description, rollout jsonb, updated_by, updated_at`. Требование ТЗ про feature-flags в монолите.

**`system_settings`** — `key, value jsonb, description, is_secret, updated_by, updated_at`.

**`idempotency_keys`** *(зеркало Redis в БД для критичных операций)* — `key, request_hash, response_status, response_body jsonb, created_at, expires_at`.

# ЧАСТЬ 9. ПОРЯДОК РЕАЛИЗАЦИИ

Последовательность выбрана так, чтобы в любой момент существовала демонстрируемая система.

1. **Каркас** — compose, Caddy, миграции, health-checks, CI. Без бизнес-логики, но разворачивается одной командой.
2. **Identity** — Keycloak realm как код, BFF-поток, RBAC, аудит. Пока нет аудита — не пишем ни одной бизнес-фичи, иначе дописывать придётся везде.
3. **Workflow-движок** — статусы, переходы, guard-условия, публикация. Самое рискованное — делаем рано.
4. **Сделки** — CRUD, переходы, история, комментарии, файлы. Появляется демо.
5. **Каталоги + импорт** — маппинг, dry-run, откат.
6. **SLA и уведомления**.
7. **Отчёты и дашборды**.
8. **Интеграции на моках** + коннектор Bitrix.
9. **Администрирование** — offboarding, erasure, feature-flags, встроенная документация.
10. **Нагрузочное тестирование, полировка UI под брендбук, презентация.**

Исходное распараллеливание по команде: identity+администрирование — один человек; workflow+сделки — двое (это ядро); импорт/экспорт/отчёты — один; фронт — один-двое; инфраструктура и интеграции — один. Контракт между фронтом и бэком — сгенерированный OpenAPI-клиент, что позволяет фронту начать на моках с первого дня.
